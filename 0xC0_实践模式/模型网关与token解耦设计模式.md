# 模型网关与 token 解耦设计模式

> 本文围绕「agent 与 token 解耦」展开：为什么把 agent 绑死在单一模型供应商上是战略风险，模型网关要承担哪三件事（多供应商竞标路由 + 失败兜底 + 统一计量），以及落地时的价格事实、开源选型与安全边界。本文是 79/80 双篇专栏的事实锚点报告。
>
> 事实来源：所有事实点逐条标注出处（素材1=模型网关技术选型；素材2=多模型路由与小模型降本设计模式；素材3=260708-GitHub开源LLMGateway项目盘点）。私有成本指标只作「某中小厂内部测算量级示意」，不作公开硬数据。

---

## 一、问题：单一模型供应商绑架的业务代价

**技术侧单点风险**（出处：素材1 第一节）：

1. 主服务商可能限流、超时、额度耗尽，或某区域临时不可用。
2. 不同任务适合不同模型（代码、长上下文、摘要、低成本批处理、本地隐私推理），单一模型无法全维度最优。
3. 上层应用不应直接感知多家服务商的鉴权方式、接口细节和错误格式。
4. 团队需要统一观察调用的错误、成本、延迟、命中模型和失败原因。
5. 生产系统需要控制日志、密钥、访问权限和审计边界。

**商业侧绑架风险**（判断，基于素材1「为什么需要模型网关」+ 素材2「大模型滥用」推演）：

- **涨价传导**：只认一家供应商进货，对方单方面涨价，成本直接传导到账单，你没有议价的第二选择。
- **条款单方变更**：限流政策、可用区、模型下线时间表都由对方说了算。
- **利润被侵蚀**：token 是 agent 产品的主要边际成本之一，被单一供应商锁死，等于把利润的定价权交给别人。

> 锚点金句：**Provider 解耦不是技术问题，是不被任何一家云厂/模型厂绑架的战略问题**（出处：上一组第二招已用，本组承接深化）。

## 二、模型网关要承担的三件事

模型网关的作用是把模型调用从「接一个 API」变成「可治理的模型调用入口」（出处：素材1 第一节）。三件事：

1. **多供应商竞标路由**（不绑死任何一家）：统一 OpenAI-compatible 入口、按消息类型/成本/SLA 选模型、负载均衡。
2. **失败兜底 fallback**（一家挂了不断供）：retry/timeout、fallback 到备用模型组、cooldown 冷却与恢复。
3. **统一计量与成本治理**（每笔都记账）：virtual key/budget、用量统计/命中模型记录、日志脱敏/审计边界。

（框架出处：素材1 第二节职责思维导图 + 第三节调用链路治理 + 第七节 fallback。）

三件事对应下篇三节骨架：**比价（路由）、兜底（fallback）、记账（计量）**——即「采购总管」比喻的三项职责。

---

## 三、多供应商路由：不绑死任何一家

**3.1 抽象层思想**：agent 代码只认一个 OpenAI-compatible 入口，供应商差异交给网关（出处：素材1 第六节）。加一家供应商时 agent 代码一行不改。

反面教材（出处：上一组第二招已点出）：直接 `if-else` 调不同 API 不是解耦——每加一家都要改 agent 代码，只是把「绑死一家」换成「绑死一堆 if-else」。**真正难点不是「有几家可换」，而是「每家接口不一样，你得有抽象层」。**

**3.2 LiteLLM model_list 配置思想**（出处：素材1 第六节示例，只保留结构，无真实 key/base_url）：

```yaml
model_list:
  - model_name: primary-coder
    litellm_params:
      model: provider-a/coder-model
      api_base: os.environ/PRIMARY_MODEL_BASE_URL
      api_key: os.environ/PRIMARY_MODEL_API_KEY
  - model_name: backup-coder
    litellm_params:
      model: provider-b/coder-model
      api_base: os.environ/BACKUP_MODEL_BASE_URL
      api_key: os.environ/BACKUP_MODEL_API_KEY
```

**3.3 OpenRouter 作为现成产品**：聚合 100+ 模型，路由策略含 Balanced（price+speed 平衡）/ Nitro（最快 throughput）/ Exacto（最高 tool-calling 准确率）（出处：上一组第二招 + 素材2 第二节）。**代价：按 token 加约 5% 服务费**（出处：素材2 2.1 节）。不种草，LiteLLM/New API/自建 Adapter 都行。

**3.4 路由策略维度**（出处：上一组第二招 + 素材1 第二节）：按消息类型选模型 / 按成本选模型（能用便宜的绝不打贵的）/ 按 SLA 选模型。

## 四、失败兜底 fallback 的正确姿势

**4.1 四个参数**（出处：素材1 第六节 litellm_settings 逐条解释）：

- `num_retries`：失败后重试次数。
- `fallbacks`：当前模型组失败后可切到哪个备用模型组。
- `allowed_fails`：失败阈值，通常表示单位时间内失败超阈值后进入 cooldown，**不应理解为「第一次失败必然冷却」**。
- `cooldown_time`：模型进入冷却后的避让时间。

**4.2 哪些错误该/不该 fallback**（出处：素材1 第七节，最关键治理细节）：

- **该 fallback**：429、额度耗尽、5xx、服务不可用、请求超时、连接中断。
- **不该直接 fallback**：401/403 认证权限错误、invalid model、tool schema 错误、请求体格式错误、明显客户端配置导致的问题。

> **fallback 不是「一个模型挂了就无脑换另一个」**。错误分类不清，fallback 反而掩盖配置问题——把 401（key 配错）当 429 去 fallback，你永远发现不了真正的 bug。

**4.3 tool call 必测**：agent 的 tool calling 稳定性还取决于上游模型是否支持 tool calls、网关是否完整透传 tool schema/tool call/streaming 字段，**必须作为 POC 必测项**（出处：素材1 第六节末 + 第九节）。

## 五、统一计量与成本治理

**5.1 计量能力**：网关在统一入口记账——virtual key、budget、用量统计、成本 tracking、命中模型记录（出处：素材1 第三节）。让「谁用了多少、走哪个模型、花多少钱」可观察可归因。

**5.2 LiteLLM vs New API 定位差异**（出处：素材1 第五节 + 素材3 横向对比）：

- **LiteLLM**：偏**调用链路治理**——统一入口、retry/fallback、负载均衡、成本观测、配置回滚。先稳「调用链路」。
- **New API**：偏**资源与渠道管理**——渠道分发、Web 后台、用户令牌、额度统计、分组权限、多格式转换。先管「模型资源」。

不是非此即彼。落地建议：**先把调用链路跑通（LiteLLM），再按需补管理后台（New API）**（出处：素材1 第五节+第十节）。

## 六、价格与降本事实

> 以下均标出处；标「⚠️ 仅通用经验」的不作硬数字引用。

**6.1 同档位模型价差能到约 50 倍**（出处：素材2 3.1 节 MMLU 价格曲线，2024-2025 数据）：

| 模型 | MMLU | 单价（/1M token） |
|------|------|------------------|
| GPT-4 系列（4o/4-turbo） | 88-92% | $5-10 |
| GPT-4o mini | 82% | $0.15 |
| Claude 3.5 Sonnet | 88% | $3 |
| Claude Haiku 4.5 | 75-78% | $0.25 |
| Qwen3.7-Plus（阿里云百炼） | 78% | ¥0.4（约 $0.06） |
| 本地 Llama-3.1-8B | 68% | $0.02-0.05（摊销） |

拐点：MMLU 75-80% 档，Haiku 4.5 $0.25 vs Qwen3.7-Plus 约 $0.06 vs 本地 7B 约 $0.03——**价差约 50 倍**。代码任务（HumanEval）本地 7B + 提示词工程可解 80% 中等难度任务（单元测试/CRUD/SQL），用不上 GPT-4（出处：素材2 3.2 节）。

**6.2 路由服务费**（出处：素材2 2.1 节）：OpenRouter 加约 5%；Not Diamond 加约 1-2%。

**6.3 本地部署吞吐**（出处：素材2 5.2 节，Hugging Face 2024 公开数据）：vLLM 的 PagedAttention + 连续批处理，GPU 利用率从约 20% 提到约 70%，吞吐约为 Ollama 的 **24 倍**。适用中型 SaaS 月调用 100 万 token 以上生产环境。

**6.4 Prompt Caching**（出处：素材2 第六节，Anthropic 2024-09 政策）：同一段上下文（系统提示词+长文档）只付一次写费，后续 5 分钟内请求的读费是写费的约 **10%**。

**6.5 私有成本示意**（⚠️ 仅作某中小厂内部测算量级示意，非公开硬数据）：某中小厂月账单约 12 万，改用路由器 + 本地 7B 做第一道分诊后降到约 4.5 万——量级示意，不同业务差异极大。

## 七、开源网关项目盘点

（出处：素材3，star/license/更新时间为 2026-07-08 GitHub 直拉；性能数据均为项目自述，未独立验证）

**第一梯队（star≥10k）**：

- **LiteLLM**（BerriAI，52.9k★，Python，MIT）：「100+ LLM 的开源 AI Gateway」，SDK + Proxy 双形态，事实标准首选。
- **New-API**（QuantumNous，41.5k★，Go，**AGPL-3.0**）：下一代 LLM 网关 + AI 资产管理，One-API 数据库兼容，国内聚合分发首选，计费/渠道/审计全，中文模型开箱。
- **One-API**（songquanpeng，35.6k★，Go+JS，MIT）：LLM API 管理分发，**已步入维护期**，建议迁 New-API。
- **APISIX**（apache，16.8k★，Lua，Apache-2.0）：云原生 API+AI Gateway，plugin 提供 LLM proxy/token rate limit/fallback/MCP-bridge，适合已有网关栈叠加 AI。
- **Portkey Gateway**（12.4k★，TS，MIT）：主打 guardrails（50+）+ 可观测 + MCP Gateway，海外产品团队模板。
- **TensorZero**（11.7k★，Rust，Apache-2.0）：⚠️ **仓库已于 2026-06-12 被作者归档（read-only），不推荐生产选型**，仅作 LLMOps 设计参考。

**选型一句话**（出处：素材3 结论）：想接得最多选 LiteLLM；国内快捷分发选 New-API；要 guardrails/企业可观测选 Portkey；已有网关栈用 APISIX 加 AI 插件。

**⚠️ 可信度声明**：所有 star/fork/更新时间为 2026-07-08 当日 GitHub 直拉；延迟、RPS 等性能数据均为各项目自述，未独立跑 benchmark；「Netflix 在用」「1% of global LLM API spend」等为项目自述，未独立溯源。

## 八、安全与公开边界

（出处：素材1 第八节）

模型网关会经过完整 prompt、上下文、工具调用参数和部分响应内容，安全边界必须放在设计前面：

- 不记录真实 API Key，不暴露内部 baseURL，日志脱敏，访问控制，密钥隔离，配置版本化，敏感数据保留周期可控。
- 公开文档只能出现：抽象模型名、环境变量占位、本地示例地址、通用架构图/流程图。
- 公开文档**不应**出现：真实 API Key/Token/Cookie/Authorization header、真实内部 baseURL、客户或公司私有模型账号、工作项目请求内容、未公开成本和业务指标。

## 九、金句素材库（围绕「进货/菜贩/采购总管」比喻）

1. agent 是厨房，token 是每天要进的食材——只认一家菜贩，人家涨价你只能认栽。
2. 直连一家模型供应商，不是「省事」，是「把定价权交出去」。
3. `if-else` 调不同 API 不是解耦，是把「绑死一家」换成「绑死一堆 if-else」。
4. 模型网关不是多接几家 API 当接口人，是给厨房配个会比价、会兜底、会记账的采购总管。
5. 比价（路由）、兜底（fallback）、记账（计量）——采购总管的三项职责，一项都不能少。
6. 会比价：同一档位的食材，价差能到 50 倍，好的采购总管让「该用便宜货的订单，绝不打到贵摊位」。
7. 会兜底：一家菜贩今天断供，采购总管立刻切到备用摊位——但不是无脑切，得先分清是「真断供」还是「你把订单写错了」。
8. fallback 不是「一个模型挂了就无脑换」，把 401（你 key 配错了）当 429 去兜底，你永远发现不了真正的 bug。
9. 会记账：每一笔进货走哪个摊位、花多少钱、谁点的，都记在账本上——这样月底对账才知道钱花哪了。
10. 解耦的真正难点不是「有几家可以换」，而是「每家接口不一样，你得有一个统一的抽象层」。
11. 先把调用链路跑通（LiteLLM），再按需补管理后台（New API）——不要一上来就想做平台。
12. 便宜不等于差：MMLU 75-80% 这一档，本地 7B 一个月的钱，够你用 GPT-4 一天——关键是把「常识题」和「专家题」分诊开。
