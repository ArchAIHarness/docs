# 定时任务与任务调度设计模式

> 行道阶段第 12 组（61+62 双篇一组）调研素材。
> 适用场景：所有"让系统在指定时间自动做某件事"的工程场景——凌晨跑批、对账、报表、清扫过期数据、通知、外部数据同步、定时发邮件、定时关单等。
> 跨单元素材、可被公开沉淀。

---

## 一、定时任务在工程里的位置

定时任务（Scheduled Job / Scheduled Task）是企业级软件里最常用、也最容易出事的一块能力。
小到"每分钟清一次过期 session"，大到"每天凌晨跑对账、月底出财务账单、年底做数据归档"——几乎每个生产系统都离不开它。

但它也是**最容易被轻视**的一块能力。
很多人以为"我写个 `setInterval` 不就行了"。
真到了生产——凌晨三点对账失败没人知道、月结报表数据不对没人发现、双 11 流量高峰某个清扫任务把数据库打挂……事故一个接一个。

行业的经验数字（⚠️ 通用经验，多家头部企业公开复盘普遍印证）：
- 一家中等规模 SaaS 公司生产环境至少有 **50-200 个**定时任务在跑（对账、清扫、报表、通知、备份、同步、归档…）
- 调查类报告显示，**凌晨 0:00-3:00 这一窗口是事故高发时段**——因为大量"对账/跑批/清扫"任务集中在这个时段启动
- 大多数"定时任务出事故"的根因不是任务本身写错，而是**调度设计有问题**：表达式错、重复执行、并发失控、没监控、没补偿

定时任务的设计不是"自动化那一段代码"——是**整套任务调度系统**。

## 二、定时任务的三大经典反模式

### 2.1 反模式一：用 setInterval 当定时任务

很多人写定时任务的起步姿势是：

```js
setInterval(() => {
    doSomething();
}, 1000 * 60 * 5);
```

问题在哪？
- 浏览器/进程一旦卡住、刷新、OOM、重启——任务就掉，**没自愈**
- 多实例部署时（负载均衡把请求轮询到 3 台机器）——**每台机器都跑一遍这个任务**，重复执行
- `setInterval` 不会"上次没跑完下次就跳过"——**任务堆叠**，可以把数据库打挂
- 任务失败后**没有任何重试机制**

**金句——"setInterval 不是定时任务，是把闹钟扔进洗衣机。转的时候响，不转的时候不响，响几次没人管。"**

### 2.2 反模式二：用数据库轮询代替调度

另一种是"写个 while 循环不停查数据库看有没有任务需要跑"。

问题在哪？
- 数据库压力暴增——**10 万条待跑任务 = 10 万次轮询**
- 任务延迟取决于轮询周期（30 秒一次？那最坏情况延迟 30 秒）
- 没法精确到分钟级（要分钟级？轮询必须每分钟开一次数据库连接）
- 服务器宕机时所有任务排队等待——**没法跨节点调度**

**金句——"用数据库轮询替代调度系统，相当于把家里的闹钟全部换成'你每 5 分钟睁眼看一次时间'——费电还总是迟。"**

### 2.3 反模式三：定时任务和业务代码揉在一起

很多团队的定时任务代码直接塞在业务 service 里——`@Scheduled(cron = "0 0 2 * * ?")` 写在某个 `@Service` 类上。

问题在哪？
- 部署时和业务一起发布——**业务回滚等于任务回滚**，定时任务版本根本没法独立管
- 排查任务问题要进业务项目的日志——**调试一塌糊涂**
- 想让某个任务临时停掉——**必须改代码发版**
- 没法做"任务编排"（任务 A 跑完跑任务 B，失败回滚）——**业务代码根本不会写这种**

**金句——"定时任务从业务里分出来，不是技术洁癖——是你半夜被叫醒时能不能 5 分钟内定位到问题。"**

## 三、定时任务的本质：三层架构

行业里成熟的定时任务系统**普遍分三层**：

### 3.1 第一层：触发层（Trigger / Scheduler）

负责"什么时候跑"——核心是 cron 表达式、间隔、固定延迟、固定速率四种触发方式。

代表：Quartz Scheduler、Spring `@Scheduled`、XXL-JOB trigger、Elastic-Job 的 cron 触发器、Linux 系统的 crontab。

cron 是 Unix 时代产物，**5 段（分/时/日/月/周）和 6 段（秒/分/时/日/月/周）写法都有**，常见的 Quarkus/Quartz 用 6 段，Linux crontab 用 5 段——**写法不一致是定时任务的常见踩坑点**。

cron 写错三类典型事故：
1. **星号忘改**：本意 `0 0 2 * * ?`（每天凌晨 2 点），手误写成 `0 0 2 * * *`（Linux 5 段，少了"周"，可能变成"每分钟"含义——不同 cron 解析器不一样）——结果**任务每分钟跑一次把数据库打挂**
2. **时区忘记设**：本意北京时间凌晨 2 点，写死在 UTC 表达式里——结果**比预计早 8 小时或晚 8 小时执行**
3. **多个 cron 表达式重叠**：原本打算分时段跑（`0 0 2 * * ?` + `0 0 14 * * ?`），某次手误复制为同一个时间——**两次触发 = 重复跑**

**金句——"cron 表达式不是给你看的，是给任务调度器精确执行的。少一个空格、多一个星号、时区忘写——半夜它就给你惊喜。"**

### 3.2 第二层：执行层（Executor / Worker）

负责"怎么跑"——核心是从调度信号到真正执行业务逻辑的过渡层。

代表：Quartz Worker、XXL-JOB Executor、Elastic-Job 的 ElasticJobExecutor、PowerJob 的 Worker、Airflow 的 Worker。

执行层必须解决三件事：
- **任务隔离**：任务 A 出问题不能影响任务 B（线程池隔离、进程隔离）
- **并发控制**：同一任务同一时刻只允许一个实例在跑（分布式锁）
- **结果回调**：任务跑完告诉调度器"我跑了、用了多久、成功还是失败"

### 3.3 第三层：业务层（Job / Business Logic）

负责"做什么"——具体的业务代码：对账、清扫、报表、通知、同步。

业务层不是给调度系统用的——是给业务方用的。
关键纪律：**业务代码必须幂等**（下面会讲）。

三层架构是行业共识——工业级定时任务框架（Quartz、XXL-JOB、Elastic-Job、PowerJob、Airflow、Temporal、AWS Step Functions）**几乎全是三层分明的**。

**金句——"定时任务和业务代码揉在一起就像把'什么时候响'、'响的时候做什么'、'做完怎么汇报'塞进同一行代码——能跑，但半夜出事你 5 分钟定位不了。"**

## 四、五道闸：让定时任务不出事

行业里把"定时任务不出事"的目标，拆成五道工程纪律——我们用家里的场景配合讲。

### 4.1 第一道闸：幂等

定义：**同一任务执行多次，结果和执行一次完全相同。**

为什么必须幂等？
- 任务重试（网络抖动、临时故障）——可能跑两次
- 任务超时（任务实际跑了 1 小时，但调度器以为挂了）——可能拉起重跑
- 分布式锁失效（Redis 重启）——同一时刻两个实例都跑

家里场景对应：**鱼缸喂食器按了两次，不会倒双倍鱼食**。
不管你按几次，鱼缸里的鱼只能吃那么多——多按只会浪费，不会把鱼撑死。

工程手段：
- 业务表加唯一索引（`UNIQUE KEY uk_task_id_run_date(...)`）——第二次插入直接 `Duplicate entry`
- 状态机（`待执行 → 执行中 → 已完成`）——状态转换幂等
- 写操作前查状态（`SELECT ... WHERE status='PENDING'` ——状态不对直接返回）
- 分布式 ID（雪花 ID / UUID）——每次跑分配唯一 run_id，用于幂等判断
- 事务表（先插一条 status=PENDING 的流水，事务提交后改 status=RUNNING / SUCCESS）——分布式场景标准做法

**金句——"幂等不是技术洁癖——它是鱼缸喂食器的'按几次只喂一次'。没这层，任务重试一次就是双倍事故。"**

### 4.2 第二道闸：分布式锁

定义：**多实例部署时，同一时刻只有一个实例能跑这个任务**。

为什么必须分布式锁？
- 任务调度器在 3 台机器上都装了——同一时间都收到了"该跑任务 A 了"的信号
- 没有锁的话——3 台都跑 = 任务并发执行 3 次
- 即便任务幂等（已经有第一道闸），**重复执行仍然浪费资源、增加数据库压力、增加下游接口 QPS**

家里场景对应：**家里两个闹钟同时响一遍**。
两个闹钟都响，会把你从睡梦中吵两次，多响一次也是浪费——你只想要"响一次、把你叫醒"。

工程手段：
- **Redis 分布式锁**（Redlock 算法 / `SET key value NX PX 30000`）：最常用，性能好，但 Redis 单点故障时锁可能失效
- **ZooKeeper 临时顺序节点**：可靠性高，但运维复杂、性能差
- **数据库唯一索引**：简单可靠，但性能差、不适合高并发锁
- **Chubby / ETCD**：Google Chubby 论文（2006 Burrows）、CoreOS ETCD 是工业级实现

**金句——"分布式锁不是技术活——它是'家里只准响一个闹钟'的规矩。两个都响，你老婆打你；两台机器都跑，你的下游打你。"**

### 4.3 第三道闸：失败重试与补偿

定义：**任务失败后，怎么恢复、怎么兜底**。

为什么必须？
- 任务可能因为瞬时故障失败（DB 抖一下、网络断 5 秒）——**重试一次就成功**
- 任务可能因为真实 bug 失败（数据脏、代码 NPE）——**重试 100 次也失败**，需要人工介入
- 任务可能因为外部依赖失败（下游 SaaS 挂了）——**等下游恢复再补跑**

家里场景对应：**闹钟没响，第二天手动调**。
机器的闹铃只负责"按点响"，响没响、响了你起没起，是另一回事。闹钟没响你不会把闹钟砸了——你会第二天手动补上。

工程手段：
- **固定间隔重试**（每 30 秒重试一次，最多 3 次）——简单但不一定合适
- **指数退避**（1 分钟、2 分钟、4 分钟、8 分钟……）——更智能，避免雪崩
- **最大重试次数 + 死信队列**（retry > 3 次的任务丢到死信队列，人工处理）
- **手动补偿操作**（重跑按钮 / 重跑某个时间段的任务）——给运维留入口
- **任务编排层的补偿**（Saga 模式 / TCC 模式）——分布式事务场景

**金句——"任务失败不可怕，怕的是失败后没人知道、没补偿机制——它会一直在那挂着，等人发现时已经过了三天。"**

### 4.4 第四道闸：监控告警

定义：**任务跑了没、跑多久、结果对不对，都有迹可循**。

为什么必须？
- 任务没跑（cron 表达式写错、调度器挂了）——业务方不知道，老板在看错的报表决策
- 任务跑挂了（异常抛出）——没人 alert，半夜出问题没人发现
- 任务跑得慢（平时 5 分钟，今天跑 1 小时）——可能下游出问题、可能脏数据

家里场景对应：**闹钟响了妈会看一眼是不是地震了**。
光响不行——还得有人听到、得有人判断"这响声对不对、是起床还是真出事"。

监控的四个层面：
1. **任务心跳**：每个任务多久汇报一次"我还活着"
2. **任务执行时长**：超过 SLA（如 30 分钟）告警
3. **任务执行结果**：成功/失败/未执行 三态清晰
4. **漏跑检测**：任务应该在 X 点跑，到了 X+5 分钟还没跑 → 告警

工具：Prometheus + Alertmanager 通用、Grafana 可视化、商业级如 Datadog APM / New Relic / 阿里云 ARMS。

**金句——"定时任务没监控，就像闹钟响了但全家都是聋子——响与不响一个样，出事当天才发现。"**

### 4.5 第五道闸：任务编排（DAG / Orchestration）

定义：**任务 A 跑完跑任务 B，B 跑完跑任务 C，失败时回滚或跳过**。

为什么必须？
- 业务流程不是单步——例如"先备份 DB → 再清扫过期数据 → 再生成日报 → 再推送通知"
- 任意一步失败，整个流程怎么办？全停？跳过？还是补偿？
- 多任务并行能提效——"清扫旧数据"和"生成日报"可以并行，不必串行

家里场景对应：**洗衣 → 烘干 → 收纳 三步走**。
衣服不会洗完就穿——还得烘干、还得叠好放进衣柜。
任何一步乱了（全塞进洗衣机忘了烘干 / 烘干完忘了收），整个流程就乱。

工程代表：
- **Apache Airflow**：Python 系，DAG 编排事实标准
- **Apache DolphinScheduler**：国产，开源
- **Temporal**：workflow-as-code，更现代
- **AWS Step Functions / Azure Logic Apps / GCP Cloud Composer**：云厂商托管
- **XXL-JOB / PowerJob 的父子任务**：国内分布式任务调度框架的轻量级编排

**金句——"任务编排不是把任务串起来——是让任务能并行能补偿、能回滚能跳过，就像洗衣服的全套流程，断一步就乱一周。"**

## 五、五类定时任务的工程菜单

行业里常见的定时任务**按业务类型分五类**，每一类都有不同的设计重心：

### 5.1 类型一：数据同步（DB → DB / DB → ES / DB → 数据仓库）

- **典型场景**：核心业务数据同步到 Elasticsearch 用于搜索；订单数据同步到数据仓库用于分析
- **设计重心**：增量 vs 全量、断点续传、源表 schema 变更兼容性
- **推荐频率**：分钟级（实时性要求高）/ 小时级（业务能用）/ 天级（报表）
- **风险点**：增量漏数据（全量补跑代价大）、断点续传失败（任务反复跑）

### 5.2 类型二：对账（多源对账）

- **典型场景**：支付系统日终对账（银行流水 vs 平台订单）；电商业务对账
- **设计重心**：幂等 + 强校验 + 告警（对账失败是资金级别事故）
- **推荐频率**：天级（凌晨跑）
- **风险点**：对账失败导致第二天的财务报表出错；漏跑导致资金缺口未发现

### 5.3 类型三：报表（数据聚合 + 输出）

- **典型场景**：日报、周报、月报、运营周报、领导看板
- **设计重心**：数据完整性 + 准确性 + 可重跑（数据出错能重出报表）
- **推荐频率**：小时级（运营报表）/ 天级（日报）/ 周月级（复盘）
- **风险点**：数据错误导致决策错误；任务超时（数据量大时跑不完）

### 5.4 类型四：清理（清扫过期/无用数据）

- **典型场景**：清扫过期 session、清扫未支付订单、清扫临时文件
- **设计重心**：避免业务高峰期跑、批量删除避免长事务、监控数据库 QPS
- **推荐频率**：小时级 / 天级
- **风险点**：跑在业务高峰期打挂数据库；批量过大锁表；误删有效数据

### 5.5 类型五：通知（推送 / 邮件 / 短信）

- **典型场景**：到期提醒、未读提醒、每日小结、营销推送
- **设计重心**：用户分批发送、熔断（下游限流时暂停）、去重（同一提醒不发两次）
- **推荐频率**：实时触发 / 小时级 / 天级
- **风险点**：下游限流误判；同一用户多次收到；敏感时段发送（半夜通知）

## 六、贯穿案例：家里的闹钟和定时器

老板布置的第 61+62 期是用"家里的闹钟和定时器"做贯穿比喻。
这套比喻的可行性论证如下：

1. **闹钟 = 简单的定时触发器**：到了 X 点就响一次响一次。
2. **定时插座 = 周期触发器**：每 X 分钟开关一次电器（鱼缸过滤 / 加氧泵）。
3. **鱼缸喂食器 = 业务任务**：到了 X 点喂一次鱼食，按两次不会倒双倍鱼食。
4. **智能家居中控 = 分布式调度中心**：协调家里所有定时任务（定时插座 + 闹钟 + 喂食器）。
5. **全屋定时系统 = 任务编排引擎**：编排"早晨流程" = "6:30 烧水 → 6:45 播放新闻 → 7:00 拉窗帘"。
6. **生物钟 + 程序响应 = 监控告警**：像人的生物钟，到了该响的时刻没响，就给你反馈。

## 七、调研素材：金句素材库（可直接用于 61/62 撰稿）

为方便撰稿阶段直接"备料"，下面汇总 30+ 条可作金句或反常识的事实点，分主题列出：

**A. 反"setInterval 当定时任务"（5 条）**

1. `setInterval` 不是定时任务——是把闹钟扔进洗衣机，转的时候响、不转的时候不响、响几次没人管。
2. 多实例部署时，`setInterval` 在每台机器上都跑一次——三个副本 = 任务并发执行三次。
3. `setInterval` 不会"上次没跑完下次就跳过"——任务堆叠，数据库打挂是早晚的事。
4. 任务失败后 `setInterval` 没有任何重试机制——失败就是失败，没人管。
5. 真正生产级的定时任务，从不用 `setInterval`——这是行业入门第一天的事。

**B. cron 表达式陷阱（5 条）**

6. cron 是 Unix 时代产物，5 段（Linux）和 6 段（Quartz）写法不一致——跨框架抄作业时**最容易翻车**。
7. cron 表达式忘设时区——本意北京时间凌晨 2 点，写死在 UTC 上，比预计早 8 小时或晚 8 小时执行。
8. cron 表达式重叠——本意分时段跑（2 点 + 14 点），手误复制成同一时间——重复触发。
9. cron 星号忘改——`0 * * * * ?`（每小时第一分钟 0 秒）和 `0 0 * * * ?`（每天 0 点）差一字，但含义是"每分钟" vs "每天一次"——每天执行变成每分钟，把数据库打挂。
10. cron 表达式里 `?` 字符（日字段与周字段二选一必须有一个为 `?`）是 Quartz 的特殊规则，Linux crontab 不支持——抄作业翻车。

**C. 失败事故反例（5 条）**

11. 2017 年 AWS S3 一项运维操作误删对象存储，导致 S3 服务大面积不可用——这是"运维操作没做保护"的经典事故，也警示**生产环境任何动作都该有定时任务级的安全围栏**。
12. 多家公司公开复盘：凌晨对账任务失败没告警，第二天财务报表用错数据——最终被监管或客户发现。
13. SaaS 平台每周清扫过期数据——某次任务没加 `WHERE status = 'EXPIRED'`，**清扫把有效订单也删了**——客户群炸锅。
14. 某支付平台对账任务因幂等键缺失——同一笔支付被退款两次，用户投诉"我没收到这笔退款"。
15. 分布式系统定时任务因 master 节点切换——同一任务在两个机房各跑一次——下游系统负载翻倍、雪崩。

**D. 鱼缸喂食器与分布式锁（5 条）**

16. 鱼缸喂食器按了两次不会倒双倍鱼食——这就是幂等的直觉。
17. 家里两个闹钟同时响——你只想要响一次——这就是分布式锁的直觉。
18. 鱼缸喂食器漏了一次鱼食——第二天手动补——这就是补偿的直觉。
19. 鱼缸水温异常没人提醒——鱼死了才发现——这就是漏跑没监控的代价。
20. 鱼缸的过滤、加氧、喂食、灯照是几个独立动作——它们通过定时器编排成"鱼缸日常"——这就是任务编排的直觉。

**E. 三层架构与五道闸（6 条）**

21. 三层架构是行业共识——触发、执行、业务——任何工业级定时任务框架都是三层分明的。
22. 定时任务从业务代码里分出来——不是技术洁癖——是你半夜被叫醒时能不能 5 分钟定位到问题。
23. 幂等不是技术洁癖——它是鱼缸喂食器的"按几次只喂一次"。
24. 分布式锁不是技术活——它是"家里只准响一个闹钟"的规矩。
25. 任务失败不可怕，怕的是失败后没人知道——它会一直在那挂着，等人发现时已经过了三天。
26. 任务编排不是把任务串起来——是让任务能并行能补偿、能回滚能跳过——像洗衣服的全套流程。

**F. 反常识与总结（4 条）**

27. 定时任务不是"自动化那一段代码"——是整套任务调度系统。
28. 定时任务不是 setInterval，是你不出门东西自己会动。
29. 定时任务跑了不算本事，跑对时间、跑对结果、还不出乱子才是。
30. 出事的从来不是"任务没设"——是"设了但忘了 WHERE"——是"跑了但没告警"——是"幂等没做所以重复执行"——是"分布式锁没做所以多个实例一起跑"。

为了让 61/62 撰稿时引用真实事实而非空谈，本节给出一些可作锚点的公开事实（如不能准确归属某一具体公司，请按"通用经验"措辞）：

3. **Elastic-Job**：当当网开源的分布式定时任务框架，与 XXL-JOB 并列为国内主流。
4. **PowerJob**：新一代分布式任务调度与计算框架，2020 年起开源，算法和易用性有改进。
5. **Apache Airflow**：Python 生态 DAG 任务编排事实标准，由 Airbnb 开源。
6. **Apache DolphinScheduler**：国产分布式任务调度 + DAG 编排系统，国内大厂广泛使用。
7. **Temporal**：workflow-as-code 框架，现代分布式任务编排理念代表。
8. **AWS Step Functions / Azure Logic Apps / GCP Cloud Composer**：云厂商托管的任务编排服务，免运维但锁定云。
9. **Linux crontab**：Unix 时代的经典定时任务方案，5 段语法，每分钟最小粒度。
10. **Spring `@Scheduled`**：Java 生态最简单易用的定时任务注解，集成在 Spring Boot 里，单机方案。
