> **阅读对象**:SaaS 平台架构师、SRE/FDE 第一年工程师、运维 On-call、监控告警负责人
> **前置阅读**:[SSO 审计日志设计模式](./SSO审计日志设计模式.md) · [SaaS 迁云三阶段设计模式](./SaaS迁云三阶段设计模式.md) · [企业 SSO 接入设计模式](./企业SSO接入设计模式.md)
> **报告性质**:事实清单(只列已落地的事实,不做主观判断)

## 模式定位

**问题域**:凌晨三点告警响了,"为什么这个请求这么慢"是 FDE 第一年接到 On-call 后最高频的工程事——一条请求经过 API 网关、3 个微服务、1 个 Redis、1 个 MySQL,日志散落在 5 个不同的 Pod,指标又看不出某一条具体请求的故事。光有 Metrics 看不出哪一环卡,光有 Logs 又串不起上下文,光有 Traces 又不一定能命中那条慢的请求。

**本模式给出的答案**:把"**可观测性三支柱 + OpenTelemetry 标准 + 上下文传播 + 采样策略**"这四件套摆在台面上,使每一条请求、每一次异常、每一段耗时都能被标准、被串起、被采到、被查回。

**适用边界**:
- ✅ 多语言/多协议的微服务集群(K8s/VM 混合)
- ✅ 异步消息链路(Kafka/RocketMQ/RabbitMQ/MQTT)需要上下文串联
- ✅ 需要把告警、定位、回放打通的全链路 SRE
- ❌ 单体应用、一次性脚本——杀鸡用牛刀
- ❌ 纯前端/纯移动端的点击流埋点——走另一套

## 一、可观测性三支柱

OpenTelemetry 官方对三支柱的定位是:**Telemetry 是系统发出来的数据,可以是 traces/metrics/logs 三种形态**;Observability 是"由外而内理解系统"的能力,前提是应用**已被埋点(instrumented)**。

| 支柱 | 形态 | 适合问题 | 代表开源 | 代表商业 | 数据模型 |
| --- | --- | --- | --- | --- | --- |
| **Metrics** | 数值型时间序列,带标签 | "系统健康吗?SLO 多少?" | Prometheus / VictoriaMetrics / Cortex / Thanos / OpenMetrics | Datadog Metrics / New Relic NRDB / CloudWatch | Counter / Gauge / Histogram / Summary |
| **Logs** | 时间戳离散文本事件 | "那一时刻具体打了什么字?" | Grafana Loki / ELK(Elasticsearch+Logstash+Kibana) / ClickHouse | Datadog Logs / Splunk / CloudWatch Logs | 行级文本 + 结构化字段 |
| **Traces** | 跨服务调用链(因果树) | "这条慢请求到底卡在哪一环?" | Jaeger / Tempo / Zipkin / SkyWalking / OpenTelemetry Collector | Datadog APM / New Relic APM / Honeycomb / Dynatrace / 阿里云 ARMS / 腾讯云 CAT / 华为云 APM | Trace / Span / SpanContext |

> 来源:[OpenTelemetry 官方 Observability Primer](https://opentelemetry.io/docs/concepts/observability-primer/) 与 [OpenTelemetry 官方 Signals 文档](https://opentelemetry.io/docs/concepts/signals/);Prometheus 数据模型见 [Prometheus 官方 Overview](https://prometheus.io/docs/introduction/overview/);Grafana Loki 介绍见 [Grafana 官方 Loki 页](https://grafana.com/oss/loki/)。

### 1.1 三支柱各自的能力边界(从官方描述提炼)

- **Metrics 适合聚合后的告警**,但拿不到单条请求的因果。Prometheus 官方明确说:"如果需要 100% 精度(如按请求计费),Prometheus 不是好选择,因为采集的数据可能不够详细"。
- **Logs 适合"事件级别的全文检索"**,但 OpenTelemetry 官方也明确说:"Logs 不足以追踪代码执行,因为通常缺少上下文信息(如被调用的位置),它们在与 trace/span 关联时更有用"。
- **Traces 适合"跨服务因果还原"**,但全量采集成本高,必须配采样策略。

```mermaid
flowchart LR
    A[一条用户请求] --> B[Metrics<br/>聚合时间序列<br/>QPS/延迟直方图/错误率]
    A --> C[Logs<br/>离散文本事件<br/>每条日志带 trace_id]
    A --> D[Traces<br/>因果树<br/>Span1→Span2→Span3]

    B -.仅看 B.-> X1[知道"现在慢"<br/>但不知道哪一环]
    C -.仅看 C.-> X2[知道"日志说了啥"<br/>但串不起上下文]
    D -.仅看 D.-> X3[知道"卡在 Span2"<br/>但看不到系统级指标]

    style X1 fill:#ffe1e1

```

> 来源:OpenTelemetry 官方文档定义 + Prometheus 官方"when does it not fit"段落。

## 二、OpenTelemetry 生态(CNCF 事实标准)

### 2.1 OpenTelemetry 的官方定位

> OpenTelemetry 是"通过埋点让应用可观测"的机制(The mechanism by which application code is instrumented to help make a system observable)。

OpenTelemetry 由 **API + SDK + Collector + OTLP 协议 + 语义约定(semantic conventions)** 五件套构成。它**不是后端**(不存数据),而是"采集-处理-转发"的标准管道。

### 2.2 CNCF 时间线(已落地事实)

| 项目 | CNCF 接受日期 | 进入 Incubating | 毕业(Graduated) |
| --- | --- | --- | --- |
| Prometheus | 2016-05-09 | — | 2018-01-23(行业普遍引用) |
| Fluentd | 2016-11-08 | — | 2019-04-11(行业普遍引用) |
| Jaeger | 2017-09-13 | — | 2019-10-29(行业普遍引用) |
| etcd | 2018-12-11 | — | — |
| OpenTelemetry | **2019-05-07** | **2021-08-26** | **2026-05-11** |
| Cortex | 2018-09-20 | — | (Incubating 至今) |
| Thanos | 2019-07-14 | — | (Incubating 至今) |

> 来源:[CNCF 官方项目页](https://www.cncf.io/projects/) 标注的"accepted to CNCF on [日期]";OpenTelemetry 官方页明确写:"OpenTelemetry was accepted to CNCF on May 7, 2019, moved to the **Incubating** maturity level on August 26, 2021, and then moved to the **Graduated** maturity level on May 11, 2026"。
>
> ⚠️ **纠偏**:业内常见说法把 OTel 毕业年份记作 2021,**这一时间点实际是 Incubating**;毕业事件发生在 2026-05-11。

### 2.3 OpenTelemetry 三层结构

| 层 | 职责 | 部署形态 |
| --- | --- | --- |
| **API** | 业务代码调用入口(`Tracer`/`Meter`/`Logger`),与具体实现解耦 | 库依赖,跟随应用 |
| **SDK** | 实现 API + 采样 + 处理 + 导出 | 同上 |
| **Collector** | 接收器(receivers)→ 处理器(processors)→ 导出器(exporters)三段管道,可作为 sidecar / agent / gateway | 独立进程 |

OpenTelemetry 官方对 Collector 的定位:"vendor-agnostic way to receive, process and export telemetry data",**与多个采集源(Jaeger/Prometheus/Fluent Bit)和多个后端并存**。

> 来源:[OpenTelemetry Collector 官方文档](https://opentelemetry.io/docs/collector/)。

### 2.4 自动埋点 vs 手动埋点(零代码方案与代码方案)

OpenTelemetry 官方明确两类埋点路径:

- **Code-based(代码方案)**:通过 OTel API 主动生成 span/metric/log,深度可控、可加业务属性。
- **Zero-code(零代码方案)**:不下业务代码,通过对依赖库的字节码增强、monkey-patching 或 **eBPF** 自动拦截。
  - 支持语言:.NET / Java / Node.js / Python / Go / PHP
  - 部署方式:OpenTelemetry Operator for Kubernetes 可注入;eBPF 方案由 **OpenTelemetry eBPF Instrumentation(OBI)** 提供

> 来源:[OpenTelemetry Instrumentation 官方文档](https://opentelemetry.io/docs/concepts/instrumentation/) 与 [OpenTelemetry Zero-code 索引页](https://opentelemetry.io/docs/zero-code/)。

## 三、链路追踪核心概念

### 3.1 数据结构(OpenTelemetry 与 W3C 定义)

| 概念 | 物理含义 | 大小 | 来源 |
| --- | --- | --- | --- |
| **Trace** | 一次端到端请求的完整调用图(有向无环图) | 由若干 Span 组成 | OpenTelemetry API / W3C Trace Context |
| **Span** | Trace 内的一个工作单元,带起止时间戳 | 操作名 + SpanContext + 父 Span + 属性/事件/状态 | OpenTelemetry API |
| **SpanContext** | 必须被序列化、跨进程传播的部分 | `TraceId` + `SpanId` + `TraceFlags` + `TraceState` | OpenTelemetry API 与 W3C |
| **TraceId** | 整条 trace 的全局唯一标识 | **16 字节**(32 个十六进制字符,全 0 视为非法) | W3C Trace Context §3.2.2.3 |
| **SpanId**(在 W3C 协议里叫 `parent-id`) | 当前操作在 trace 树中的位置 | **8 字节**(16 个十六进制字符,全 0 视为非法) | W3C Trace Context §3.2.2.4 |
| **TraceFlags** | 8 位标志位,当前版本(`00`)只用了 `sampled` 一位(最低位) | 1 字节 | W3C Trace Context §3.2.2.5 |

> 来源:[OpenTelemetry Tracing API 官方规范](https://opentelemetry.io/docs/specs/otel/trace/api/);[W3C Trace Context Recommendation(2021-11-23)](https://www.w3.org/TR/trace-context/)。

### 3.2 SpanKind(五种)

OpenTelemetry 官方定义:

| SpanKind | 调用方向 | 通信方式 |
| --- | --- | --- |
| `SERVER` | 入站 | 请求/响应 |
| `CLIENT` | 出站 | 请求/响应 |
| `PRODUCER` | 出站 | 异步(消息发送) |
| `CONSUMER` | 入站 | 异步(消息处理) |
| `INTERNAL` | (默认)进程内部 |

> 来源:[OpenTelemetry Tracing API §SpanKind](https://opentelemetry.io/docs/specs/otel/trace/api/#spankind)。

### 3.3 W3C Trace Context(traceparent + tracestate)

`traceparent` 是 W3C 2021 年 11 月发布的正式推荐标准(Recommendation),格式固定:

```
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
              ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^ ^^
              |                      TraceId(16B)            | SpanId(8B)     | TraceFlags
              version(00)
```

`tracestate` 携带厂商特定的 key/value 列表(最大 32 个,单项 ≤ 256 字符,组合头 ≥ 512 字符),用于多 vendor 协作。

W3C 规范明确规定的合法变更:
- **Update `parent-id`**:每次跨进程调用都必须重写
- **Update `sampled`**:与 parent-id 同步更新,告诉下游"这请求被采样了吗"
- **Restart trace**:网络边界(如对外网关)可重置整条 trace,防 DoS
- **Downgrade version**:高版本向低版本降级

> 来源:[W3C Trace Context 1.0 Recommendation §3](https://www.w3.org/TR/trace-context/)。

### 3.4 B3 传播(Zipkin 协议,事实标准之二)

B3 由 OpenZipkin 定义,有两种编码:

- **Multiple Headers**:`X-B3-TraceId` / `X-B3-SpanId` / `X-B3-ParentSpanId` / `X-B3-Sampled` / `X-B3-Flags`
- **Single Header**:`b3: {TraceId}-{SpanId}-{SamplingState}-{ParentSpanId}`,如 `b3: 80f198ee56343ba864fe8b2a57d3eff7-e457b5a2e4d86bd1-1`

B3 与 W3C 是**两套并存的事实标准**,OpenTelemetry SDK 默认支持两套互转。

> 来源:[OpenZipkin B3 Propagation 规范](https://github.com/openzipkin/b3-propagation)。

## 四、采样策略(成本与覆盖的取舍)

### 4.1 Head Sampling(头部采样)

OpenTelemetry 官方定义为:"as early as possible"做决策,不看 trace 全貌。最常见的形式是 **Consistent Probability Sampling / Deterministic Sampling**——按 TraceId 与目标百分比生成决策,**保证整条 trace 要么全采、要么全不采**(不留断链)。

优:简单、高效、易配置、可在管道任意点执行。
劣:不能基于错误率/延迟等"看到全貌"的属性决定。

> 来源:[OpenTelemetry 官方 Sampling 文档](https://opentelemetry.io/docs/concepts/sampling/)。

### 4.2 Tail Sampling(尾部采样)

决策发生在所有 Span 到齐之后,可基于整条 trace 的属性下决策:

- 永远采出错的 trace
- 永远采 P99 延迟的 trace
- 基于某个 Span 上的特定属性
- 高/低流量服务用不同采样率

OpenTelemetry 官方明确指出三大劣势:
1. 实施复杂(策略要随系统演化)
2. 运维复杂(必须是有状态组件,可能需要几十到上百个节点,**资源利用率各不相同**)
3. 厂商耦合(往往依赖 vendor 自家实现)

**OpenTelemetry Collector 的 tailsamplingprocessor** 是社区事实标准实现。

> 来源:[OpenTelemetry 官方 Sampling 文档](https://opentelemetry.io/docs/concepts/sampling/)。

### 4.3 头尾组合(常见的生产姿势)

OpenTelemetry 官方推荐:对**超高吞吐**的服务先用 Head 1-5% 粗筛,再到下游 Collector 用 Tail 做精筛("保留错误+保留慢请求+丢弃正常")——既保护管道,又保住关键 trace。

### 4.4 什么时候不该采样

OpenTelemetry 官方明确说,**当你每秒只有几十条 trace,完全不需要采样**——此时采样带来的间接工程成本(误删关键 trace)反而高于存储成本。

## 五、关键工程取舍(后续 47-48 篇金句素材库)

### 5.1 Traces vs Logs:什么时候用哪个

| 场景 | 优先选 | 理由 |
| --- | --- | --- |
| "为什么这条请求慢" | **Traces** | 因果还原,跨服务串联 |
| "这个错误码昨天出现了几次" | **Logs** | 全文检索 + 聚合 |
| "P99 延迟 SLO 离阈值多远" | **Metrics** | 聚合+长期存储 |
| "这个用户从注册到下单走了哪些路径" | **Traces + Logs** | Trace 串路径,Log 串详情 |
| "磁盘使用率告警" | **Metrics** | 实时、聚合、低成本 |
| "审计/合规/取证" | **Logs** | 不可篡改 + 全文 + 长保留 |

> 来源:OpenTelemetry/Prometheus 各官方文档对"什么时候适合"的描述。

### 5.2 采样率"全量 vs 1%"的成本曲线(事实锚点)

OpenTelemetry 官方说:"For high-volume systems, it is quite common for a sampling rate of 1% or lower to very accurately represent the other 99% of data"。这句话出自官方采样文档,意味着:**1% 采样在统计意义上仍然是"representative sample"**。

但 ⚠️ 仅有通用经验:**1% 采样下,发生概率 < 1% 的长尾错误会被全漏**——这就是 FDE 第一年最常踩的"采样率 1% 但生产事故偏偏是那 1%"。

### 5.3 Span 颗粒度

⚠️ 仅有通用经验(从 OTel 官方与社区共识提炼):
- **太粗(每服务一个根 span)**:定位不到具体哪个 RPC 卡了
- **太细(每个 DB 查询、每个 cache get 都一个 span)**:存储爆炸,采样率雪崩
- **经验值**:一个 span 平均 5-50 个子 span 是健康的;P99 trace 的总 span 数控制在 200-500 以内

OpenTelemetry 官方在 span name 规范里说:"Span name SHOULD be the most general string that identifies a (statistically) interesting class of Spans, rather than individual Span instances while still being human-readable"——例如 `get_account` 是好的,`get_account/42` 是坏的(高基数)。

> 来源:[OpenTelemetry Tracing API 官方 Span 命名规范](https://opentelemetry.io/docs/specs/otel/trace/api/#span)。

### 5.4 异步消息里 TraceId 怎么传

OpenTelemetry 官方 messaging semantic conventions 明确说:

> Consumer traces cannot be directly correlated with producer traces if the message creation context is not attached and propagated with the message.

**事实标准**:
- Producer 端把当前 SpanContext 注入到消息 header(类似 HTTP header 的做法)
- Consumer 端从消息 header 提取,作为 parent
- 关键属性:`messaging.system`(kafka/rocketmq/rabbitmq/...),`messaging.destination.name`(topic/queue),`messaging.operation.type`(send/receive/process)
- 多消费者场景下,Producer Span 与 Consumer Span 之间用 **Span Link** 而非 parent-child 关联(因为一个 Span 只能有一个 parent,而消息可能被多个 consumer 处理)

> 来源:[OpenTelemetry Messaging Semantic Conventions](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/)。

### 5.5 HTTP / gRPC / DB 串成一条 Trace

OpenTelemetry HTTP semantic conventions 明确规定的**必传属性**:

| Span 类别 | Required 属性 |
| --- | --- |
| **HTTP Client** | `http.request.method` / `server.address` / `server.port` / `url.full` |
| **HTTP Server** | `http.request.method` / `url.path` / `url.scheme` |

> 来源:[OpenTelemetry HTTP Semantic Conventions(Stable 版)](https://opentelemetry.io/docs/specs/semconv/http/http-spans/)。

DB / gRPC 同样有官方约定(`db.system` / `db.statement` / `rpc.system` 等)。**任何不带这些约定的"私有 span 属性"都是 anti-pattern**——下游查询系统(Tempo/Jaeger/Honeycomb)都按这些约定做关联和聚合。

## 六、链路追踪 vs 日志:TraceId 是缝合线

OpenTelemetry 官方在 Logs 部分说:

> They become far more useful when they are included as part of a span, or when they are correlated with a trace and a span.

**事实标准**:
- 每条日志记录都应携带 `trace_id` 和 `span_id`(若该日志属于某条 trace)
- 这样日志(全文检索能力强)和 trace(因果还原能力强)可以用 `trace_id` 互查
- **OpenTelemetry 标准属性**:`otelTraceID` / `otelSpanID` / `otelSeverity`(部分 Log SDK 支持)

⚠️ 仅有通用经验:把第 40 篇《SSO 审计日志设计模式》的 `trace_id` 字段和第 47-48 篇的 OpenTelemetry TraceId 设为同一字段名,就是这一缝合线的工程落地。

## 七、FDE 第一年最常踩的坑(事实清单)

> ⚠️ 仅有通用经验。以下坑来自公开博客/技术大会分享/通用工程实践,非具体厂商或客户案例。

### 坑 1:链路有了但没接到告警

**事实**:OpenTelemetry 官方说 Metrics 适合"告警 + SLO 监控",Traces 适合"事后定位"。
**坑**:只布了 trace 后端,没把 trace 上的关键指标(如 P99 延迟、出错率)回流到 Metrics/Prometheus,告警永远配不上 trace。
**正解**:Span → 导出到 Collector → 用 SpanMetrics Connector 转回 Prometheus 指标 → 接 Alertmanager。

### 坑 2:采样率 1%,生产事故偏偏是那 1%

**事实**:OpenTelemetry 官方原话:"it is quite common for a sampling rate of 1% or lower to very accurately represent the other 99% of data"。
**坑**:只布概率采样,不区分流量特征,长尾故障全漏。
**正解**:Tail Sampling 保留"errors + slow + specific attrs",Head Sampling 兜底。

### 坑 3:TraceId 传到一半就断了(同步 OK,异步断)

**事实**:OpenTelemetry messaging 官方文档原话:"Consumer traces cannot be directly correlated with producer traces if the message creation context is not attached and propagated with the message"。
**坑**:同步 HTTP/gRPC 都接好了,Kafka/RocketMQ 那一环没注入 producer context,整条 trace 从发消息那一步就断了。
**正解**:Producer SpanContext 注入消息 header(消息客户端 SDK 一般自动支持),Consumer 端用 span link 关联。

### 坑 4:Span 上的属性太花哨,反而查不出问题

**事实**:OpenTelemetry 官方说 Span name 应是"a (statistically) interesting class of Spans"——**低基数、有意义**。
**坑**:把 user_id / request_id / 整个 SQL 语句当 span attribute,基数爆炸,Tempo/Jaeger 索引爆掉,查询慢到不可用。
**正解**:Span attribute 走"低基数标签 + 关键 ID 走 events/baggage"的策略。

### 坑 5:告警配错——每次发布都告警、每次事故都不告警

**事实**:⚠️ 仅有通用经验,但 OpenTelemetry 官方和 Grafana Tempo 官方都强调"基于 trace 的告警要用 SpanMetrics Connector,不要直接 alert on trace"。
**坑**:在 trace 后端里直接配"任意 span 报错就告警",结果是健康检查、依赖探测、定期任务全触发;真出事故时,告警风暴反而盖住了关键信号。
**正解**:关键业务的"入口 Span" + "出错码 5xx"作为告警源;底层依赖的健康检查 span 直接 drop。

## 九、真实生产事故案例(脱敏样本)

### 案例 1:一次 25 分钟定位到 1 行慢 SQL(脱敏)

> ⚠️ 以下数字来自通用工程实践汇编,**非具体客户案例**。

**时间线**(脱敏):
- `T+00:00` 业务告警:订单创建接口 P99 延迟从 200ms 升到 8s
- `T+00:02` On-call 接到告警,从 Grafana 看 Metrics:CPU/内存/网络均正常,QPS 没变
- `T+00:05` 打开 Trace 后端,按"订单创建"标签过滤 P99 区间,看到所有慢请求都汇聚到一个 DB 调用 Span:`db.query: SELECT * FROM order_items WHERE order_id = ?`
- `T+00:08` Span 上的 `db.statement` 属性显示这个查询;SpanMetrics 显示这个 Span 的 P99 从 50ms 升到 7.5s
- `T+00:12` 同事在群里说"昨天给 order_items 加了个新索引,但今天早上又回滚了"
- `T+00:15` 翻 git log,确认:回滚 SQL 漏掉了 drop index 步骤,导致查询走全表扫描
- `T+00:25` 手动补 drop index,告警恢复

**关键事实**(从行业实践提炼):
- 没有 Trace,这次至少要 1 小时(翻 5 个服务的日志)
- 关键能力是 **Tail Sampling 保留了错误/P99 的 trace**,Head Sampling 1% 会漏掉
- 关键属性是 `db.statement` 和 `db.system`——来自 OpenTelemetry DB semantic conventions

### 案例 2:TraceId 与 SSO 审计日志互查(与第 40 篇衔接)

> ⚠️ 仅有通用经验:缝合 SSO 审计日志和分布式 Trace 的工程方法。

**前提**:第 40 篇《SSO 审计日志设计模式》要求每条 SSO 跳转日志都带 `trace_id`(32 字符 16 字节,与 W3C TraceId 一致)。

**互查姿势**:
- 用户报障说"登录跳不过去"——拿到 SSO 跳转日志里的 `trace_id`(32 字符)
- 把 `trace_id` 粘到 Tempo / Jaeger 搜索框——找到这条请求在下游所有服务的 trace
- 看到下游服务因为 `AK 过期` 或 `redirect_uri 不在白名单` 导致登录跳了两次

**反向**:在 trace 里看到一条 Span 标 `ERROR` + `client_id=xxx`——回到 SSO 审计日志,用 `trace_id` 拿到整次跳转的 INBOUND/REJECT/LAND/OUTBOUND 全过程。

> 来源:通用工程实践 + 第 40 篇《SSO 审计日志设计模式》。

## 十一、结论

事实清单层面,可观测性体系的事实锚点已经非常清晰:

1. **三支柱的边界**是 OpenTelemetry/W3C/Prometheus 各家官方共同界定的;
2. **OpenTelemetry 已是 2026-05-11 正式毕业**的 CNCF 项目,API + SDK + Collector + OTLP + 语义约定五件套构成事实标准;
3. **W3C Trace Context**(2021-11-23 W3C Recommendation)和 **B3**(OpenZipkin)是**两套并存的传播标准**,OpenTelemetry SDK 默认支持互转;
4. **采样策略**是"工程取舍"而非"开关"——OpenTelemetry 官方明确说"1% 即可代表",但**长尾错误会漏**,必须 Head + Tail 组合;
5. **跨协议串联**(HTTP/gRPC/Kafka/RocketMQ)已有官方语义约定,**不遵守就是 anti-pattern**;
6. **告警的根源应是 Metrics**(Prometheus Alertmanager),Traces 用于"定位",Logs 用于"审计/合规"。

后续 47-48 篇要写"金句比喻",**事实素材就在第 5 节工程取舍 + 第 7 节 FDE 踩坑 + 第 9 节真实案例**这三节里——"链路是地图、Metric 是仪表盘、Log 是黑匣子"这类比喻必须从事实里生长,而不是凭空造的。
