## 一、问题背景：为什么「一人一 pod」是中小厂 Agent 的烧钱黑洞

### 1.1 先讲清楚 agent 的「身体」

要理解成本从哪来，得先理解一个 agent 是由什么拼成的。业界目前比较一致的分层是这样的：

| 组件 | 角色 | 特性 |
|---|---|---|
| **大模型** | 脑袋 | 无状态、按 API 调用、认知不持久化 |
| **沙箱 / 容器** | 身体 | 有状态执行体、持有工作目录、进程、工具连接 |
| **MCP / Tool** | 手脚 | 通过标准协议给身体接上操作外部世界的能力 |
| **会话服务** | 记忆 | 服务层维护对话上下文与过程内容 |

关键在于：**没有身体的大模型只是聊天机器人，有身体才成 agent**。大模型本身是无状态的，你调一次 API 它回一次话，它不记得你、不持有你的文件、也不能帮你跑命令。真正让 agent「能干活」的，是那个常驻的、有状态的「身体」——一个能读写文件、跑进程、连工具的执行环境。

> **⚠️ 仅有通用经验**：「身体怎么分配，直接决定了成本和隔离的所有取舍」这一判断是行业里反复被验证的工程经验，但没有统一的量化基准。

### 1.2 「一人一 pod」是怎么变成烧钱黑洞的

最直觉、最安全的做法，是给**每个在线用户分配一个独立的容器（pod）**，里面装着这个用户专属的运行环境，数据通过网络存储（如 NAS）挂载进去。这样隔离性极强——用户 A 的文件和进程，和用户 B 物理隔开，不会串。

代价是：**每一个在线用户，就等于一台常驻的云主机**。这台「云主机」要烧四份钱：

1. **内存钱**：运行时（IDE 服务端 + agent 内核 + 工具进程）常驻内存，哪怕用户在发呆，内存也占着。
2. **镜像钱与磁盘钱**：每个 pod 要拉一份沉重的容器镜像，镜像越大，磁盘和拉取带宽越贵。
3. **冷启动的时间成本**：用户点开产品到 agent 可用，要等 pod 拉镜像、起服务、加载上下文——这段时间用户在干等，体验差，还得靠预留资源来缓解，预留就是钱。
4. **调度密度的机会成本**：单 pod 越重，一台物理节点能塞的 pod 越少，同样的服务器只能服务更少的用户。

这套模型最致命的地方在于**成本随用户量线性上涨，收益却往往次线性**：

> 用户从 100 涨到 10000，基础设施成本几乎是 100 倍地涨；但收益（尤其是 C 端消费级产品的客单价）远远跟不上这个斜率。1 万个用户花的钱 ≈ 100 ×（100 个用户花的钱），永远做不出规模效应。

**这就是中小厂做 C 端 Agent 的第一道生死关**：验证阶段（几十个用户）成本 hold 得住，一旦要真正运营（成千上万用户），成本模型直接把商业模式压垮。

> **出处**：公开可查的成本结构佐证——AWS Lambda 官方明确其计费是「按分配内存 × 执行时长（GB-秒）」计价，内存可在 128MB–10240MB 间调节，CPU 与资源随内存成比例分配（[AWS Lambda Pricing](https://aws.amazon.com/lambda/pricing/)）。这说明**云计算的定价锚点就是内存 × 时长**——你占的内存越大、常驻时间越长，钱烧得越多。「一人一 pod 常驻」恰恰是「大内存 × 长时长」的最贵组合。

### 1.3 为什么不能靠「换隔离方式」省钱

一个常见的误区是：既然一人一 pod 太贵，那就改成「多人共享一个实例」不就省了？

事实是，对已经把隔离押在 pod 边界上的团队，**隔离方式不是可以随便动的软参数，而是既定事实**。改隔离意味着重做数据安全模型、重估故障爆炸半径——这是架构级的地震，不是省钱的第一选择。

> **⚠️ 仅有通用经验**：共享实例路线本身也有代价。公开资料显示，共享实例池（Shared Instance Pool）需要额外解决 WebSocket/SSE 会话亲和、文件命名空间重定向、Extension Host 隔离三件事（[coder/code-server issues](https://github.com/coder/code-server/issues)、[OpenSumi overview](https://opensumi.com/en/docs/integrate/overview)、[Theia docs](https://theia-ide.org/docs/extensions/)）。省下的实例钱，可能又搭进技术债里。

真正的突破口不在「要不要隔离」，而在「**pod 本身太重**」。身体太胖，才是病根。所以第一招不去动隔离，而去做一件更聪明的事——**给 pod 减肥，把身体的一部分搬到用户自己的电脑上去扛**。

## 二、核心概念：「运行环境下沉浏览器」到底是什么

### 2.1 一句话解释

**把 agent「身体」里负责「渲染层 / 交互层」的那部分，从云端 pod 搬到用户自己的浏览器里去跑；云端 pod 只留下真正的「大脑」——agent 内核 + 插件。**

打个比方：

> 原来你雇了一个全职管家（pod），他 24 小时住在你家隔壁的酒店房间（云主机），房费你全掏。后来你发现，管家的工作里有一大半是「站在你面前端茶递水、摆盘、报菜名」——这些其实可以让你自己家的智能音箱（浏览器）来做。管家只需要留在酒店里负责「动脑子决策」，门面活儿交给你家已有的设备。酒店房间立刻可以退到更小、更便宜的档次。

### 2.2 拆开看：IDE 的「三个进程」哪部分能下沉

现代 Web IDE 框架（如 OpenSumi、Theia）在架构上通常拆成三个进程（[OpenSumi 官方文档](https://opensumi.com/en/docs/integrate/overview)）：

- **Frontend Process（前端进程）**：跑在浏览器里，负责渲染界面、处理用户交互。
- **Backend Process（后端进程）**：跑在服务端 Node 进程里，负责文件、终端等系统能力。官方明确其后端实现是**无状态的**，每个连接对应独立的 DI 容器，连接之间严格隔离。
- **Extension Process（扩展进程）**：跑扩展 / 插件，有完整的 Node.js API 权限。

而像 code-server 这类产品，本质是「**把整个 VS Code 跑在服务端**，浏览器只当显示器」（[coder/code-server](https://github.com/coder/code-server)）。这就是「重后端」的典型——渲染、交互、执行全在云端，浏览器只负责画像素。code-server 官方给出的单实例最低配置要求是 **1 GB RAM + 2 vCPU**（[coder/code-server README](https://github.com/coder/code-server)），这基本就是「一人一后端」的地板价。

**下沉的核心动作，就是把「渲染 + 交互」这部分从后端进程剥出来，让它在浏览器里原生跑**。OpenSumi 官方提供了纯前端形态（lite / CodeBlitz），通过 `BrowserFsProvider` / `HttpFileService` 把「文件」映射成 HTTP 接口，前端可以脱离 Node 后端独立运行（[OpenSumi lite 文档](https://opensumi.com/en/docs/integrate/quick-start/lite)）。微软官方的 VS Code for the Web（vscode.dev）也是同一思路——「**完全运行在浏览器里、零安装**」，把编辑、浏览、语法高亮都放到浏览器沙箱里跑（[VS Code for the Web 文档](https://code.visualstudio.com/docs/setup/vscode-web)）。

### 2.3 下沉之后，云端 pod 里还剩什么

下沉后，云端 pod 的职责收窄到只剩「大脑 + 手脚」：

- **OpenCode 一类的 agent 运行时内核**（负责调度大模型、编排工具）
- **业务插件 / skill / MCP 编排**（负责具体场景能力）

界面渲染、编辑器交互、面板布局这些「门面活儿」，全部让用户浏览器扛。**pod 从「全功能工作站」瘦成「决策内核」**。

> **⚠️ 为方案测算，非真实生产数据**：某中小厂的内部性能方案里，把这条演进路径量化为——前期形态（渲染在云端）单 pod 约 1Gi 内存；渲染下沉浏览器后，单 pod 可降到约 256Mi 量级。此为方案测算目标值，非已验证的生产事实，仅作「下沉能显著减负」的量级示意。

## 三、为什么能降本：成本模型拆解

下沉浏览器不是「感觉上更省」，而是能沿着一条清晰的因果链，把成本一环一环压下去。

### 3.1 因果链：上游是资源，下游是体验

```
单 pod 变轻（内存↓ + 镜像↓）
   ↓ 使得
单节点能塞的 pod 变多（密度↑）
   ↓ 使得
预热池（warm pool）有了经济性
   ↓ 使得
冷启动从「被动扛」变成「主动预热」
   ↓ 使得
Agent 加载时间大幅缩短
   ↓ 使得
用户可感知的等待变短（体验↑）
```

**关键洞察**：最上游是资源开销，最下游才是用户能感受到的「快慢」。想压下游的体验延迟，必须先动上游的成本结构。而「下沉浏览器让 pod 变轻」正是撬动整条链的第一块多米诺骨牌。

### 3.2 省钱环节逐个拆

**① 单 pod 内存下降 → 直接省内存钱**

云计算按内存计价（[AWS Lambda Pricing](https://aws.amazon.com/lambda/pricing/)）。渲染层搬到浏览器后，pod 内不再跑沉重的 IDE 服务端进程，常驻内存显著下降。内存降一半，同样的服务器预算能服务的用户数就能翻倍。

> **⚠️ 为方案测算，非真实生产数据**：某中小厂方案测算，单 pod 内存 limit 从 1Gi 压到 384Mi 量级（含尚未拔除的渲染服务端），进一步去掉渲染服务端后目标是 256Mi。仅作量级示意。

**② 镜像瘦身 → 省磁盘钱 + 省冷启时间**

pod 不再需要打包完整的 IDE 服务端及其一大堆前端静态资源，镜像可以显著变薄。镜像越薄，节点拉取越快，冷启动的「拉镜像」这一段耗时随之下降。

> **⚠️ 为方案测算，非真实生产数据**：某中小厂方案把 runtime 镜像从 1.5GB+ 目标压到 500MB 以内（含渲染服务端），去掉后目标 300MB。仅作量级示意。

**③ 单节点密度提升 → 摊薄每用户的固定成本**

pod 变轻之后，同一台物理节点（比如 8Gi 内存）能同时承载的 pod 数量大幅增加。密度上去了，每个用户分摊到的节点固定成本（操作系统、调度开销、网络）就被摊薄。

> **⚠️ 为方案测算，非真实生产数据**：某中小厂方案测算单 8Gi 节点承载 pod 数从约 8 提升到 20+。仅作量级示意，「密度翻倍级提升」是这类下沉的典型收益方向。

**④ warm pool 有了经济性 → 冷启动可以被「预热」掉**

这一步是「下沉」真正的杠杆点。所谓 warm pool（预热池），就是**提前起好一批空的 pod 待命**，用户请求一到，直接从池子里拿一个绑给他，省掉现起 pod 的冷启时间。

但 warm pool 有个天生的经济学难题：**预热的 pod 是在「空烧钱」**——没人用也占着内存。如果单 pod 很重（1Gi），维持一个像样的预热池成本高到不可接受；一旦单 pod 变轻（256Mi 量级），同样的预算能预热的 pod 数量翻好几倍，warm pool 才从「奢侈品」变成「日用品」。

> **一句话**：pod 不减肥，warm pool 就是个烧钱的摆设；pod 减了肥，warm pool 才养得起。这就是为什么「下沉」是「预热」的前置。

**⑤ 冷启动被压下去 → 用户等待变短**

有了经济可行的 warm pool，用户请求命中预热池时，几乎跳过了「建 pod + 拉镜像 + 起服务」的全部冷启开销，加载时间从「几十秒」量级压到「秒级」。

> **⚠️ 为方案测算，非真实生产数据**：某中小厂方案里，pod 冷启从 30s+ 目标压到热连 ≤1.5s、冷启 ≤5.5s，命中率目标 ≥70%。仅作量级示意，非已验证生产数据。

### 3.3 用公开数据给「冷启动有多贵」定个锚

冷启动不是玄学，业界有公开量级可参照：

- **Serverless 冷启动优化**：AWS Lambda 为解决冷启专门推出 SnapStart 与 Provisioned Concurrency——官方明确 SnapStart 能把启动从「几秒」压到「亚秒级」（sub-second），靠的正是「快照预初始化内存 + 缓存」（[AWS Lambda Pricing · SnapStart](https://aws.amazon.com/lambda/pricing/)）。这跟「warm pool 预热」是同一个思路：**把初始化挪到用户请求之前**。
- **Provisioned Concurrency（预置并发）**：官方描述是「让函数保持初始化、hyper-ready，双位数毫秒内响应」（[AWS Lambda Pricing](https://aws.amazon.com/lambda/pricing/)）——本质就是「花钱养一个预热池」，代价是「你为配置的并发量和时间付费」。这印证了 warm pool 的经济学：**预热能换极速，但预热本身要花钱，所以让被预热的单元越轻越好**。
- **纯浏览器运行时的极端对照**：StackBlitz 的 WebContainer 把 Node.js 运行时整个搬进浏览器标签页，官方声称「毫秒内拉起整个开发环境」「比 localhost 还快」「计算在本地完成，不用为云 VM 按分钟付费」（[WebContainers 文档](https://webcontainers.io/guides/introduction)）。这就是「下沉」走到极致的样子——**云端零运行时，冷启动趋近于零**。

## 四、工程手段原理（讲清原理，不涉私有细节）

「下沉」是主干，但要让 pod 真正瘦下来、warm pool 真正转起来，还要一整套配套工程手段。下面每一条只讲公开可理解的原理与比喻。

### 4.1 镜像分层瘦身

**原理**：容器镜像是分层的，多个镜像可以共享相同的底层。把「不变的公共层」（基础系统、运行时）和「常变的业务层」（插件、配置）拆开，公共层被所有 pod 复用，只有业务层需要单独存储和分发。再配合多阶段构建，把编译工具、用不到的语言运行时统统排除在最终镜像之外。

> **比喻**：不要每个人都背一整套厨房出门，公共的锅碗瓢盆放在共享厨房，各人只带自己的调料包。

### 4.2 进程瘦身

**原理**：一个 pod 里往往塞了一堆进程——渲染服务端、agent 内核、各种工具进程。下沉把渲染服务端整个拿掉后，再对剩下的进程做「运行时参数收敛」：限制内存堆上限、关掉用不到的遥测 / 自动更新、把启动期的安装动作前移到镜像构建期。进程少了、每个进程占的内存有上限，单 pod 的内存水位自然下来。

### 4.3 共享 sidecar

**原理**：有些能力是「只读的、无状态的、大家都要用的」——比如某些通用检索工具、模板库。与其每个 pod 各自跑一份（N 份内存），不如抽出来做成一个**集群共享的服务（sidecar / 独立部署）**，所有 pod 通过网络连过去用。

> **比喻**：小区里每家不用各装一台净水器，楼下装一台大的，各家接管子用。用户私有数据仍留在各自 pod 里（隔离不破），只有公共能力被共享。

### 4.4 warm pool 池化

**原理**：见 §3.2 第 ④ 点。核心是「**空 pod 提前起好待命，用户来了现绑**」。绑定动作要做到原子化：给空 pod 打上用户标记、挂载该用户的数据卷、通知内核切换工作目录、更新路由索引。关键前提是——**待命的空 pod 不挂任何用户数据，认领时才挂**，这样隔离性一点不损失。

### 4.5 上下文预烘焙

**原理**：agent 启动时要加载一堆上下文（角色定义、技能、工具配置）。如果每次都「全量拉」，启动就慢。预烘焙的思路是：**把通用的、全站共享的上下文提前打进基础镜像**，启动时直接就地读；把场景差异化的部分放到共享存储里按需懒加载（第一次用到某个技能才加载它）。

> **比喻**：常用的调料提前备在灶台上（预烘焙进镜像），冷门的香料放在储藏室，用到再去拿（懒加载）。

### 4.6 会话粘性

**原理**：用户中途离开又回来，如果每次都重新起 pod，就白白吃一次冷启。会话粘性通过一个「用户 → pod」的路由索引（配合 TTL 续期），让用户重连时**优先找回上次那个还活着的 pod**，直接接着用，跳过全部加载链路。这也解决了 WebSocket/SSE 长连接的会话亲和问题——公开方案里常用一致性哈希、Sticky Session、或 Redis 索引来做（[coder/code-server issues](https://github.com/coder/code-server/issues)）。

### 4.7 首字流式

**原理**：大模型是一个 token 一个 token 往外吐的。与其等整段回答生成完再一次性显示（用户干等），不如**收到第一个 token 就立刻往屏幕上渲染**，让用户第一时间看到「AI 已经开始回答了」。这不减少总时长，但把「可感知的等待」大幅缩短。

> **公开印证**：AWS Lambda 专门提供 HTTP Response Streaming，官方说明其目的正是「改善 Time to First Byte（首字节时间），在函数生成第一批 HTML 时就渲染到浏览器」（[AWS Lambda Pricing · HTTP Response Stream](https://aws.amazon.com/lambda/pricing/)）。首字流式是行业通用的体验优化范式。

### 4.8 意图短路缓存

**原理**：用户的请求里，有相当一部分是「闲聊、导航、固定问答」这类轻量意图，根本不需要惊动完整的 agent 内核。**在网关层放一个轻量模型或规则库先做一次意图判定**：命中闲聊/导航就直接秒回，命中业务请求才透传给 pod。再叠加一层结果缓存——相同技能 × 相同参数 × 相近上下文的输出直接走缓存，不重复计算。

> **比喻**：前台接待先接一道——「问洗手间在哪」这种，前台直接答了，不用惊动里屋的专家；只有真正的业务问题才往里传。

## 五、演进路径：为什么下沉是「前置」而不是「终点」

「运行环境下沉浏览器」不是一步到位的开关，而是一条前中后三段的演进曲线。理解这条曲线，才明白为什么第一招是「前置」。

| 阶段 | 形态 | 渲染在哪 | 云端 pod 里有什么 | 云端负担 |
|---|---|---|---|---|
| **前期**（起步生产） | 云端全套 | 云端（IDE 服务端） | IDE 服务端 + agent 内核 + 插件 | 最重 |
| **中期**（下沉渲染） | 渲染下沉浏览器 | 用户浏览器 | agent 内核 + 插件 | 中等 |
| **后期**（整体进浏览器） | agent 整体进浏览器 web vm | 用户浏览器 | 近乎只剩静态托管 + LLM 网关 | 最轻 |

> **⚠️ 为方案测算，非真实生产数据**：上表的三段式演进及其资源量级来自某中小厂的内部路线设计。中期目标是把渲染层搬进浏览器、pod 侧只留 agent 内核；后期设想借助浏览器内 WASM 虚拟机（类似 QEMU-WASM / WebContainer 路线）把整个 agent 搬进浏览器。中后期均为方案设想，非已上线事实。

### 5.1 为什么必须是「前置」

三段式演进有一个严格的依赖顺序：

- **前期 → 中期的门槛**：中期要把渲染搬走，但前提是 **pod 侧的 agent 内核先得瘦到能被 warm pool 经济地预热**。如果内核本身还很胖，就算渲染搬走了，pod 依然重、密度依然低、预热依然养不起——中期就是空中楼阁。
- **所以「下沉 + 瘦身」是中期启动的前置作业**：先在前期形态里把 agent 内核压到中期能承接的水位，中期上线时只需「前端切换到纯浏览器渲染 + 后端拔掉渲染服务端」两个动作，不用再做一次大瘦身。
- **后期是长期愿景**：把整个 agent（连内核带执行）都塞进浏览器 WASM 虚拟机，云端趋近于零运行时。这是「下沉」的理论终点，但依赖浏览器内运行时的成熟度，属于远期方向。

> **一句话**：下沉浏览器是「保命三招」的第一招，因为它不是省一笔钱，而是**把后面所有省钱动作的地基先打好**——密度、预热、快启动，全都踩在「pod 变轻」这块地基上。

### 5.2 三种形态在业界都有活的对照

这条演进不是凭空设想，公开技术里三种形态都有成熟实现：

- **重后端形态**：code-server、OpenVSCode Server——VS Code 整个跑在服务端，浏览器当显示器（[coder/code-server](https://github.com/coder/code-server)）。
- **渲染下沉形态**：OpenSumi lite/CodeBlitz、VS Code for the Web——前端在浏览器原生跑，后端可选（[OpenSumi lite 文档](https://opensumi.com/en/docs/integrate/quick-start/lite)、[VS Code for the Web](https://code.visualstudio.com/docs/setup/vscode-web)）。
- **整体进浏览器形态**：StackBlitz WebContainer——连 Node 运行时都在浏览器 WASM 里（[WebContainers 文档](https://webcontainers.io/guides/introduction)）。

**事实说明**：这三种形态并非替代关系，而是「云端负担」从重到轻的一条光谱。中小厂沿着这条光谱往轻的方向走，就是在给成本模型松绑。

## 六、边界与代价：下沉不是银弹

任何架构选择都有代价，把话说全才是负责任的科普。

### 6.1 能力边界：浏览器沙箱跑不了什么

微软官方明确列出了 VS Code for the Web 的限制：**终端和调试器在浏览器里不可用**，因为你没法在浏览器沙箱里编译、运行、调试一个原生程序（[VS Code for the Web · Limitations](https://code.visualstudio.com/docs/setup/vscode-web)）。扩展也只有「能在浏览器沙箱里运行的子集」可用——纯声明式的主题、片段、语法可以直接跑，需要跑代码的扩展必须改造成 Web 版。

**对 agent 的含义**：渲染和交互可以下沉，但**真正要跑命令、编译、执行不可信代码的「重活」，仍然离不开云端的执行环境**。所以「下沉」下沉的是门面（渲染 / 交互），不是全部——身体的「手脚」该留云端还得留。

### 6.2 前端能力受限的代价

OpenSumi 的纯前端形态（lite/CodeBlitz）只能加载 **Web Extension 子集**，扩展列表还得预先静态声明，装不上完整的 VSIX（[OpenSumi lite 文档](https://opensumi.com/en/docs/integrate/quick-start/lite)）。这意味着下沉渲染是有「功能税」的——换来了轻量，牺牲了一部分插件生态的完整度。要不要付这个税，取决于你的 agent 产品到底需不需要那些重扩展。

### 6.3 命中率不是越高越好

warm pool 的命中率追求要克制。命中率追到 95% 的经济学并不划算——要按峰值 × 缓冲留一个大池子空烧钱。合理做法是**命中率追一个够用的水位（比如 70%），剩下的少数派走冷启动兜底**，因为冷启动经过前面的瘦身之后已经压到可接受区间了。

> **⚠️ 仅有通用经验**：具体命中率的经济平衡点因业务峰谷形态而异，没有统一最优值。

### 6.4 依赖用户设备

下沉把一部分负担转移给了用户浏览器。这意味着**低端设备、老旧浏览器上的体验会打折**。这是「把身体的一部分让用户扛」的另一面——你省了云端的钱，但把一部分算力压力转给了用户的设备。VS Code for the Web 官方也提示，Webview 在不同浏览器上可能表现不一致（[VS Code for the Web · Browser support](https://code.visualstudio.com/docs/setup/vscode-web)）。

## 七、金句素材库（供撰稿改写为比喻 / 金句）

> 以下均为可作比喻或金句的事实点，供 77/78 篇撰稿时改写。带 ⚠️ 的为方案测算量级，不可当生产事实写死。

1. **没有身体的大模型只是聊天机器人，有身体才成 agent。** —— agent 四件套里，沙箱才是身体，大模型只是脑袋。

2. **每一个在线用户，就等于一台常驻的云主机。** —— 一人一 pod 模型下，用户在发呆，内存也在烧钱。

3. **云计算的定价锚点是「内存 × 时长」，而一人一 pod 常驻恰恰是最贵的那个组合：大内存 × 长时长。** （出处：[AWS Lambda Pricing](https://aws.amazon.com/lambda/pricing/)）

4. **1 万个用户花的钱 ≈ 100 ×（100 个用户花的钱）——线性成本永远做不出规模效应。** —— 这是中小厂 C 端 Agent 的第一道生死关。

5. **下沉浏览器，就是让管家留在酒店动脑子，端茶递水的门面活儿交给你家的智能音箱。** —— 云端只留大脑，身体的一部分让用户浏览器扛。

6. **code-server 的「地板价」是 1GB 内存 + 2 vCPU 起——这就是「一人一后端」的最低门票。** （出处：[coder/code-server README](https://github.com/coder/code-server)）

7. **pod 不减肥，warm pool 就是个烧钱的摆设；pod 减了肥，warm pool 才养得起。** —— 这是「下沉是预热的前置」最凝练的一句。

8. **预热的本质，是把初始化挪到用户按下发送之前。** —— AWS SnapStart 把冷启从几秒压到亚秒，靠的就是「快照 + 缓存」预初始化（出处：[AWS Lambda · SnapStart](https://aws.amazon.com/lambda/pricing/)）。

9. **Provisioned Concurrency 就是「花钱养一个预热池」，代价是你为闲着的并发也付费——所以被预热的单元越轻越好。** （出处：[AWS Lambda Pricing](https://aws.amazon.com/lambda/pricing/)）

10. **下沉走到极致，就是 WebContainer——云端零运行时，冷启动趋近于零，「比 localhost 还快」。** （出处：[WebContainers 文档](https://webcontainers.io/guides/introduction)）

11. **镜像分层瘦身：别每个人都背一整套厨房出门，公共锅碗放共享厨房，各人只带调料包。**

12. **共享 sidecar：小区里不用每家装一台净水器，楼下装一台大的，各家接管子用。**

13. **首字流式：不是让 AI 说得更快，而是让用户第一时间看到「它已经开始说话了」。** —— 总时长没变，但「可感知的等待」被砍掉一大截（出处：[AWS Lambda · HTTP Response Stream](https://aws.amazon.com/lambda/pricing/)）。

14. **意图短路：问洗手间在哪，前台直接答了，不用惊动里屋的专家。** —— 闲聊 / 导航不进 pod。

15. **下沉浏览器省的不是一笔钱，而是把后面所有省钱动作的地基先打好——密度、预热、快启动，全踩在「pod 变轻」这块地基上。** —— 这就是它为什么是「第一招 / 前置」。

16. **浏览器沙箱跑不了终端和调试器——下沉的是门面（渲染 / 交互），不是身体的手脚。** （出处：[VS Code for the Web · Limitations](https://code.visualstudio.com/docs/setup/vscode-web)）

17. **换来轻量，要付「功能税」：纯前端形态只能跑 Web Extension 子集，装不上完整 VSIX。** （出处：[OpenSumi lite 文档](https://opensumi.com/en/docs/integrate/quick-start/lite)）

18. **命中率不是越高越好——追 95% 要按峰值留大池空烧钱，追 70% 用冷启兜底反而更划算。** —— warm pool 的经济学是「够用即可」。

19. **下沉是把一部分算力压力转给用户设备——你省了云端的钱，低端设备的体验就得打折。** —— 天下没有免费的下沉。

20. **前期云端全套、中期渲染下沉、后期整体进浏览器——这不是三个方案，是云端负担从重到轻的一条光谱。** —— 中小厂沿光谱往轻走，就是在给成本松绑。

21. **同一个「把初始化挪到请求之前」的思路，Serverless 叫 SnapStart / 预置并发，容器世界叫 warm pool——名字不同，招式一样。** （出处：[AWS Lambda Pricing](https://aws.amazon.com/lambda/pricing/)）

22. **微软官方 vscode.dev 已经把整个 VS Code 塞进浏览器「零安装」跑起来了——「下沉」不是激进设想，是巨头已经走通的路。** （出处：[VS Code for the Web](https://code.visualstudio.com/docs/setup/vscode-web)）
