# AI 行业常用术语速查与梳理

刚接触 AI 这行的人，多半都被一堆缩写搞晕过：MCP、A2A、RAG、RLHF、MoE、KV Cache……一句话里能蹦出五六个，听着像暗号。

其实没那么玄。这些词大多是某个具体问题被反复讨论，大家懒得每次都解释一遍，就约定俗成缩成了一个词。知道它当初要解决什么麻烦，这个词基本就记住了。

下面按六块来理：协议、模型、智能体、训练、工程、部署。每条给全称、中文和一句人话解释。像 ACP 这种一个缩写指两样东西的，我会专门点出来。

> 这篇只管术语本身，不去追某个最新模型叫什么名字——名字换得太快，搞清楚词背后的门道更划算。

## 一、协议类：让模型和智能体能互相对话

这块是最近两年讨论得最多的。模型一旦要调工具、要跟别的智能体配合，就得有个统一的说法，不然每接一个工具都得重写一遍适配，谁都受不了。

| 缩写 | 全称 | 说明 |
|---|---|---|
| **MCP** | Model Context Protocol（模型上下文协议） | Anthropic 提出，让模型用统一方式接外部工具、数据、提示模板。有人叫它“AI 的 USB-C”。目前用得最广。 |
| **A2A** | Agent2Agent（智能体到智能体协议） | Google 提出，解决不同厂商、不同平台的智能体怎么互相发现和协作，偏企业级。 |
| **ACP** | Agent Communication Protocol（智能体通信协议） | 规范智能体之间怎么通信。出自 IBM 的 BeeAI，后来交给了 Linux 基金会。 |
| **ACP** | Agent Client Protocol（智能体客户端协议） | 同一个缩写的另一个意思，Zed 编辑器提的，专门管 IDE 跟 AI 编码助手怎么对接。 |
| **AG-UI** | Agent-User Interaction Protocol | 管智能体跟前端界面怎么交互，让 Agent 能驱动页面。 |

ACP 这个缩写得小心，社区里它能指两样完全不同的东西——一个是智能体之间通信，一个是编辑器跟智能体对接。写文章、做分享的时候最好写全称，不然读者容易看岔。

记这几个词，可以按“往哪个方向连”来分：MCP 往下连工具和数据，A2A 和 ACP 横着连别的智能体，AG-UI 往上连用户界面。

## 二、模型和架构

| 缩写 | 全称 | 说明 |
|---|---|---|
| **LLM** | Large Language Model（大语言模型） | 拿海量文本训出来、靠上下文猜下一个 token 的模型，比如 GPT、Claude。 |
| **LRM** | Large Reasoning Model（大推理模型） | 答之前先“想一通”的模型，会显式推理，数学、代码、复杂逻辑更强。 |
| **MoE** | Mixture of Experts（混合专家） | 模型内部分成好多“专家”子网络，每次只用其中几个，参数能堆很大但算力不至于爆。 |
| **VLM / MLLM** | Vision / Multimodal LLM | 能同时看图、听声、读文字的多模态模型。 |
| **SLM** | Small Language Model（小语言模型） | 参数小、能塞进手机或边缘设备跑，图个便宜和隐私。 |
| **Transformer** | 变换器架构 | 现在几乎所有大模型的底层架构，核心是注意力机制。 |
| **Attention** | 注意力机制 | 处理某个词的时候，让模型自己判断该多看其他哪些词。Transformer 全靠它。 |
| **Embedding** | 嵌入 / 向量化 | 把文字、图片转成一串数字向量，这样语义就能算、能检索了。 |
| **Context Window** | 上下文窗口 | 模型一次最多能看多少 token，比如 128K、1M，决定了能喂多长的输入。 |

简单说，Transformer 和 Attention 是地基，LLM、LRM、MoE、VLM 是地基上盖的不同房子，侧重点不一样而已。

## 三、智能体相关

智能体（Agent）就是让模型别光会答话，能自己定计划、调工具、一步步把事干完。这一类词讲的都是“AI 怎么动手做事”。

| 术语 | 说明 |
|---|---|
| **Agent / Agentic** | 智能体 / 有自主性的。能盯着一个目标，自己规划、调工具、看反馈再调整。 |
| **ReAct** | Reasoning + Acting，边想边做：想一步、做一步、看看结果再继续。很经典的做法。 |
| **CoT** | Chain of Thought，思维链。让模型把推理过程一步步写出来，复杂题答得更准。 |
| **ToT** | Tree of Thoughts，思维树。在思维链基础上同时试几条路再挑最好的，适合要试错的题。 |
| **Multi-Agent** | 多智能体协作。几个 Agent 分工，比如一个做规划、一个执行、一个审查。 |
| **Function Calling / Tool Use** | 函数调用 / 工具使用。模型自己判断该调哪个工具，并把参数填好。 |
| **Human-in-the-loop** | 人在回路。关键或高风险的步骤要人点头确认，是 Agent 安全的关键。 |
| **Memory** | 记忆。分短期（当前上下文）和长期（外部存储），让 Agent 跨轮、跨会话还记得事。 |

这几个词的关系大致是：CoT、ToT 管怎么想，ReAct 管怎么把想和做接起来，Tool Use 管怎么动手，Human-in-the-loop 管别让它闯祸。

## 四、训练和对齐

这一块讲模型从“能力很糙”到“听话、好用、安全”是怎么练出来的。

| 缩写 | 全称 | 说明 |
|---|---|---|
| **Pre-training** | 预训练 | 拿海量数据训出一个通用底座，最烧钱的一步。 |
| **SFT** | Supervised Fine-Tuning（监督微调） | 用人工标的“问题—答案”数据，教模型按指令办事。 |
| **RLHF** | RL from Human Feedback（基于人类反馈的强化学习） | 用人对答案好坏的偏好，把模型调得更有用、更安全。 |
| **DPO** | Direct Preference Optimization（直接偏好优化） | RLHF 的简化版，直接拿偏好数据优化，工程上更省事更稳。 |
| **RLVR** | RL with Verifiable Rewards（可验证奖励的强化学习） | 用客观能验证的奖励（代码跑没跑通、答案对不对）来训，推理模型常用。 |
| **Alignment** | 对齐 | 让模型行为符合人的意图和价值观，是个统称。 |
| **LoRA** | Low-Rank Adaptation（低秩适配） | 只训一小撮额外参数就能微调，省钱省卡，定制门槛大降。 |
| **Distillation** | 蒸馏 | 拿大模型当老师教小模型，把能力压进更小的个头。 |
| **Fine-tuning** | 微调 | 在底座模型上针对具体场景再训一遍的统称。 |

顺一遍就是：预训练让它见多识广，SFT 教它听话，RLHF / DPO / RLVR 让它把话说好、把事做对，LoRA 和蒸馏解决怎么便宜地拥有它。

## 五、工程实践

这块是干活的人天天碰的。核心矛盾就一句：模型输出是概率性的、不稳定的，但工程系统要的是确定、可靠、能管。

| 术语 | 说明 |
|---|---|
| **Prompt Engineering** | 提示词工程。琢磨怎么写输入，让模型答得更好。 |
| **Context Engineering** | 上下文工程。比提示词工程更全面，管的是模型“看到的全部东西”——指令、记忆、检索结果、工具定义怎么组织在一起。 |
| **RAG** | Retrieval-Augmented Generation（检索增强生成）。先去知识库捞相关资料，再让模型照着资料答，是治“幻觉”的主力。 |
| **GraphRAG** | 基于知识图谱的 RAG，靠实体和关系来检索，多跳推理、关系类问题更拿手。 |
| **Hallucination** | 幻觉。模型一本正经地胡说，看着合理其实是编的。 |
| **Guardrails** | 护栏。对模型的输入输出做安全、合规、格式上的约束，别让它越界。 |
| **Eval / Evals** | 评测。用测试集和指标量模型到底行不行，是迭代的尺子。 |
| **Grounding** | 接地 / 事实锚定。把答案绑到真实数据源上，能追溯、能核对。 |

这一类说白了都在干一件事：用工程手段把模型的不确定性框住。RAG 和 Grounding 管答得对不对，Guardrails 管能不能说，Eval 管到底好不好，Prompt 和 Context 决定你到底喂了它什么。

## 六、推理和部署

模型训完，真正面对用户的是“推理”这一步。这块的词基本都跟成本、延迟、吞吐有关。

| 术语 | 说明 |
|---|---|
| **Token** | 模型处理文本的最小单位。计费、上下文长度、性能指标全按它算。 |
| **Inference** | 推理。模型实际跑起来出结果的过程，线上算力主要花在这。 |
| **Quantization** | 量化。把权重精度降下来（比如 FP16 降到 INT8/INT4），用更少显存换得起部署。 |
| **KV Cache** | 键值缓存。把已经算过的中间结果存下来，别重复算，长文本生成提速主要靠它。 |
| **TTFT** | Time To First Token，第一个字吐出来要等多久，决定用户的“等待感”。 |
| **TPOT** | Time Per Output Token，每个字平均多久，决定生成“顺不顺”。 |
| **Throughput** | 吞吐量。单位时间能处理多少 token，决定能扛多大并发。 |
| **Batching** | 批处理。把多个请求合在一起算，提高 GPU 利用率和吞吐。 |

部署这事本质上是在“质量、延迟、成本”三者之间找平衡：量化和蒸馏压成本，KV Cache 和 Batching 提吞吐，TTFT、TPOT 是量体验的尺子。

## 几句使用建议

新词会一直冒出来，但有三个习惯能让你不被名词牵着走：

1. **先问它解决什么问题**。每个缩写背后都有个具体痛点——MCP 治工具接入乱，RAG 治幻觉，量化治部署贵。抓住痛点，名字就是个标签。
2. **留意一词多义**。ACP 这种不止一种意思的不少，正式场合写全称，省得读者看岔。
3. **按这六块归类记**。协议、模型、智能体、训练、工程、部署——新词冒出来时，先想它该落在哪一块，剩下的就是往格子里填东西。

把这套分类摸熟了，再多新名词，无非是往已有的格子里再塞几个。
