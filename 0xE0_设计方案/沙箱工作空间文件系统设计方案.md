# 沙箱工作空间文件系统设计方案

> **阅读对象**:平台工程师、沙箱系统设计者、AI IDE 架构师
> **前置阅读**:[OpenCode 全体系深度解析](../0xD0_实践指南/OpenCode全体系深度解析.md)
>
> 本文系统化拆解面向沙箱环境的轻量级版本化文件系统设计。

---

## 前言

工作空间，本质是一套**复刻 Git 底层核心对象模型、剔除冗余概念、具备强边界隔离的轻量级版本化文件系统**。

Git 的核心价值，源于 Blob、Tree、Commit 三层对象模型——以哈希寻址实现内容去重，以树形结构记录文件快照，以提交链形成完整变更历史。但标准 Git 附带分支、合并、远程、引用等大量拓展能力，同时依赖外部二进制程序，概念繁杂、部署笨重，不适用于轻量化、强隔离、跨语言调用的基础文件服务场景。

工作空间完全继承 Git 三层对象内核，彻底剥离无关拓展能力，不依赖任何外部程序，通过纯自研实现**版本快照、变更追溯、环境回滚**三大核心能力。系统最核心的设计，是构建严格的**空间边界**，将整个文件环境划分为业务区与系统区，边界物理隔离、权限隔离、逻辑隔离，各司其职互不干扰。

## 一、设计哲学：取 Git 精华，去 Git 冗余

### 本章要点

| 核心概念 | 一句话说明 |
|---------|-----------|
| Git 三层对象模型 | Blob 存内容、Tree 存结构、Commit 存变更，三层构成版本化内核 |
| 精简取舍 | 保留核心对象模型，剔除分支/合并/远程等全部拓展能力 |
| 纯自研实现 | 不依赖外部二进制，无语言绑定，HTTP REST 标准通信 |

### 1.1 Git 核心对象模型

Git 的版本化能力，本质上由三层对象模型驱动，每一层各司其职：

```mermaid
flowchart TB
    subgraph GitModel["Git 核心对象模型"]
        Blob["Blob 对象<br/>存储文件内容<br/>SHA256 哈希寻址"]
        Tree["Tree 对象<br/>存储目录快照<br/>记录路径与关联"]
        Commit["Commit 对象<br/>存储变更提交<br/>链式串联历史"]
    end

    Blob --> Tree --> Commit

    style Blob fill:#e1f5fe
    style Tree fill:#e8f5e9
    style Commit fill:#fff3e0
```

| 对象 | 职责 | 标识方式 |
|------|------|---------|
| **Blob** | 存储单个文件的完整内容 | SHA256 内容哈希 |
| **Tree** | 记录某一时刻的全量目录结构 | 关联路径 + Blob 哈希 |
| **Commit** | 记录一次完整变更 | 链式哈希指向父提交 |

### 1.2 工作空间的精简取舍

标准 Git 在三层对象模型之上，叠加了大量拓展能力。工作空间的设计哲学是：**只取内核，不留外壳**。

```mermaid
flowchart LR
    subgraph StandardGit["标准 Git 全集"]
        G1[Blob / Tree / Commit]
        G2[Branch 分支]
        G3[Merge 合并]
        G4[Remote 远程]
        G5[Ref 引用]
        G6[外部二进制依赖]
    end

    subgraph Workspace["工作空间精简集"]
        W1[Blob / Tree / Commit]
        W2[纯自研实现]
        W3[HTTP REST 接口]
    end

    G1 ==> W1
    G2 -.->|剔除| X1[✗]
    G3 -.->|剔除| X2[✗]
    G4 -.->|剔除| X3[✗]
    G5 -.->|剔除| X4[✗]
    G6 -.->|剔除| X5[✗]

    style StandardGit fill:#ffc9c9
    style Workspace fill:#c8e6c9
```

| 维度 | 标准 Git | 工作空间 |
|------|---------|---------|
| 核心对象模型 | Blob / Tree / Commit | **完整保留** |
| 分支与合并 | Branch / Merge / Rebase | 剔除 |
| 远程与引用 | Remote / Ref / Tag | 剔除 |
| 运行依赖 | 外部二进制程序（git CLI） | **纯自研，零外部依赖** |
| 通信协议 | Git 自有协议 | **HTTP REST + JSON** |
| 语言绑定 | 与 CLI 强耦合 | **跨语言兼容** |

### 1.3 核心能力聚焦

剔除冗余之后，工作空间聚焦三大核心能力：

```mermaid
flowchart TB
    Core["工作空间核心能力"]

    C1["版本快照<br/>任意时刻的全量文件状态捕获"]
    C2["变更追溯<br/>完整历史链，任意版本可回溯"]
    C3["环境回滚<br/>一键还原至任意历史版本"]

    Core --> C1 & C2 & C3

    style Core fill:#5c7cfa,color:#fff
    style C1 fill:#e1f5fe
    style C2 fill:#e8f5e9
    style C3 fill:#fff3e0
```

## 二、空间边界：业务区与系统区的强隔离

### 本章要点

| 核心设计 | 一句话说明 |
|---------|-----------|
| 双区隔离 | 业务区完全开放 + 系统区永久锁死，物理隔离、权限隔离、逻辑隔离 |
| toc.yml | 业务文件的节点层级与路径映射，纳入版本管控 |
| .workspace | 系统隐藏目录，仅内核可操作，外部无任何权限 |

### 2.1 整体目录结构

工作空间根目录为全域存储载体，根目录下仅存在两个固定项：

```mermaid
flowchart TB
    Root["工作空间根目录 /"]

    Toc["toc.yml<br/>业务文件节点层级与路径映射<br/>纳入版本管控"]

    WS[".workspace/<br/>系统隐藏目录<br/>外部无权访问"]

    Biz["其余全部空间<br/>业务区 - 完全开放自定义"]

    BlobDir["blob/<br/>Blob 对象存储"]
    TreeDir["tree/<br/>Tree 对象存储"]
    CommitDir["commit/<br/>Commit 对象存储"]

    Root --> Toc
    Root --> WS
    Root --> Biz
    WS --> BlobDir
    WS --> TreeDir
    WS --> CommitDir

    style Root fill:#dee2e6
    style Toc fill:#ffd43b,color:#000
    style WS fill:#ff6b6b,color:#fff
    style Biz fill:#69db7c,color:#000
    style BlobDir fill:#ffc9c9
    style TreeDir fill:#c9f0ff
    style CommitDir fill:#fff3c9
```

### 2.2 业务区：完全开放的自由空间

业务区占据根目录下除 `toc.yml` 和 `.workspace` 之外的全部空间，具备以下特征：

- 支持任意目录、文件的自定义创建、修改、删除
- 满足各类业务的灵活存储需求
- 所有变更均被系统内核实时感知
- 与 toc.yml 同等纳入版本管控

### 2.3 系统区：锁死的版本内核

`.workspace` 系统目录是版本化能力的核心载体，具备三重锁定：

| 锁定维度 | 说明 |
|---------|------|
| **结构锁死** | 内部仅含 blob/、tree/、commit/ 三个固定子目录，永久不可变更 |
| **权限锁定** | 外部任何程序、任何用户均无权进入修改、增删、读写 |
| **逻辑锁定** | 仅系统内核可操作，这是保障版本内核稳定的根本 |

```mermaid
flowchart LR
    subgraph 外部["外部进程 / 用户"]
        E1[HTTP 接口调用]
        E2[文件系统直接访问]
        E3[其他程序]
    end

    subgraph 内核["系统内核"]
        K[版本化内核<br/>唯一授权操作者]
    end

    subgraph 系统区[".workspace 系统区"]
        S1[blob/]
        S2[tree/]
        S3[commit/]
    end

    E1 -->|请求转发| K
    E2 -->|拒绝访问| X[⛔]
    E3 -->|拒绝访问| X
    K -->|唯一授权读写| S1 & S2 & S3

    style 外部 fill:#ffc9c9
    style 内核 fill:#c8e6c9
    style 系统区 fill:#e1f5fe
```

### 2.4 三重隔离机制

```mermaid
flowchart TB
    subgraph 隔离体系["三重隔离保障"]
        P1["物理隔离<br/>业务区与系统区目录物理分离<br/>互不干扰"]
        P2["权限隔离<br/>系统区仅内核可写<br/>外部完全只读或不可见"]
        P3["逻辑隔离<br/>业务操作不感知版本存储细节<br/>版本操作不干预业务逻辑"]
    end

    P1 --> R["各司其职<br/>安全可控"]
    P2 --> R
    P3 --> R

    style 隔离体系 fill:#5c7cfa,color:#fff
    style R fill:#69db7c,color:#000
```

## 三、底层对象模型：Blob、Tree、Commit

### 本章要点

| 对象 | 职责 | 去重机制 |
|------|------|---------|
| Blob | 存储单个文件内容 | 相同内容 SHA256 相同，只存一份 |
| Tree | 记录全量目录快照 | 关联 Blob 哈希，结构可复用 |
| Commit | 链式串联变更历史 | 父提交哈希 + 当前 Tree 哈希 |

### 3.1 Blob —— 内容寻址的存储单元

Blob 对应单个文件的内容，通过 **SHA256 哈希值**作为唯一标识。

```mermaid
flowchart LR
    subgraph 文件["业务区文件"]
        F1["report.md<br/>内容: Hello World"]
        F2["notes.txt<br/>内容: Hello World"]
        F3["data.json<br/>内容: {key: val}"]
    end

    subgraph BlobStore["Blob 存储"]
        B1["a1b2c3...<br/>Hello World"]
        B2["d4e5f6...<br/>{key: val}"]
    end

    F1 -->|"SHA256"| B1
    F2 -->|"SHA256<br/>相同内容 → 同一 Blob"| B1
    F3 -->|"SHA256"| B2

    style 文件 fill:#e8f5e9
    style BlobStore fill:#e1f5fe
```

**核心优势**：相同内容的文件只存储一份，实现极致存储去重。无论业务区有多少份内容相同的文件，Blob 层始终只保留一份物理存储。

### 3.2 Tree —— 全量目录快照

Tree 对应某一时刻的全量目录快照，记录三项关键信息：

| 字段 | 说明 |
|------|------|
| 路径 | 文件在目录树中的完整路径 |
| 文件类型 | 文件 / 目录 |
| 关联 Blob 哈希 | 指向对应的内容存储 |

```mermaid
flowchart TB
    subgraph Snapshot["Tree 快照示例"]
        T["Tree 对象<br/>hash: t7u8v9..."]
        T1["路径: /docs/report.md<br/>类型: file<br/>Blob: a1b2c3..."]
        T2["路径: /docs/notes.txt<br/>类型: file<br/>Blob: a1b2c3..."]
        T3["路径: /config/data.json<br/>类型: file<br/>Blob: d4e5f6..."]
        T4["路径: /images/<br/>类型: directory"]
    end

    T --> T1 & T2 & T3 & T4

    style Snapshot fill:#e8f5e9
```

### 3.3 Commit —— 链式变更记录

Commit 对应一次完整变更提交，包含五项核心信息：

```mermaid
flowchart TB
    subgraph CommitChain["Commit 链式结构"]
        C1["Commit v1<br/>hash: c1a2b3<br/>parent: ∅<br/>tree: t1x2y3<br/>time: 2024-01-01<br/>msg: 初始化"]
        C2["Commit v2<br/>hash: c4d5e6<br/>parent: c1a2b3<br/>tree: t4u5v6<br/>time: 2024-01-02<br/>msg: 新增文档"]
        C3["Commit v3<br/>hash: c7g8h9<br/>parent: c4d5e6<br/>tree: t7w8x9<br/>time: 2024-01-03<br/>msg: 修改配置"]
    end

    C1 --> C2 --> C3

    style C1 fill:#e1f5fe
    style C2 fill:#e8f5e9
    style C3 fill:#fff3e0
```

| 字段 | 说明 |
|------|------|
| 提交哈希 | 当前 Commit 的唯一标识 |
| 父提交哈希 | 指向上一次 Commit，形成链式结构 |
| 关联 Tree 哈希 | 指向本次提交时刻的目录快照 |
| 提交时间 | 变更发生的时间戳 |
| 提交说明 | 人工或自动生成的变更描述 |

### 3.4 三对象联动关系

三层对象通过哈希引用串联，形成完整的版本化数据结构：

```mermaid
flowchart TB
    C["Commit 对象<br/>记录变更 + 关联 Tree"]

    T["Tree 对象<br/>记录目录快照 + 关联 Blob"]

    B1["Blob 对象 A<br/>文件内容 A"]
    B2["Blob 对象 B<br/>文件内容 B"]
    B3["Blob 对象 C<br/>文件内容 C"]

    C -->|"tree_hash"| T
    T -->|"blob_hash"| B1
    T -->|"blob_hash"| B2
    T -->|"blob_hash"| B3

    CP["父 Commit"] -->|"parent_hash"| C

    style C fill:#fff3e0
    style T fill:#e8f5e9
    style B1 fill:#e1f5fe
    style B2 fill:#e1f5fe
    style B3 fill:#e1f5fe
    style CP fill:#f3e0ff
```

## 四、三层架构设计

### 本章要点

| 层级 | 职责 | 关键特征 |
|------|------|---------|
| 协议接入层 | 接收请求、参数校验、路径防穿透 | 单一入口、安全拦截 |
| 核心能力层 | 文件操作、版本提交、差异对比、环境回滚 | 全部核心逻辑 |
| 底层存储层 | Blob / Tree / Commit 持久化 | 纯对象存储、无业务逻辑 |

### 4.1 整体分层架构

系统自上而下分为三层，单向依赖，上层调用下层，下层不感知上层：

```mermaid
flowchart TB
    subgraph L1["协议接入层"]
        A1["HTTP REST 接口"]
        A2["参数校验"]
        A3["路径防穿透拦截"]
        A4["JSON 数据格式"]
    end

    subgraph L2["核心能力层"]
        B1["文件操作"]
        B2["目录管理"]
        B3["对象哈希计算"]
        B4["版本提交"]
        B5["差异对比"]
        B6["环境回滚"]
    end

    subgraph L3["底层存储层"]
        C1["Blob 持久化"]
        C2["Tree 持久化"]
        C3["Commit 持久化"]
    end

    L1 --> L2 --> L3

    style L1 fill:#e1f5fe
    style L2 fill:#e8f5e9
    style L3 fill:#fff3e0
```

### 4.2 协议接入层

协议接入层是系统对外的唯一窗口，承担两项核心职责：

**请求接收与参数校验**：所有外部调用通过 HTTP REST 标准协议接入，统一以 JSON 作为数据交互格式，完成跨语言兼容。无论是 Java、Go、Python 还是其他开发语言，均可通过标准化接口完成全量操作。

**路径防穿透拦截**：对每个请求做严格的路径合法性校验，拒绝访问 `.workspace` 目录及外部路径，保障业务区隔离安全。

### 4.3 核心能力层

核心能力层实现系统的全部核心逻辑，包含六大能力模块：

```mermaid
flowchart TB
    subgraph Capabilities["核心能力层 · 六大模块"]
        M1["文件操作<br/>创建 / 修改 / 删除"]
        M2["目录管理<br/>创建 / 遍历 / 删除"]
        M3["对象哈希<br/>SHA256 计算 / 去重"]
        M4["版本提交<br/>Blob + Tree + Commit 生成"]
        M5["差异对比<br/>任意版本间变更比对"]
        M6["环境回滚<br/>还原至任意历史版本"]
    end

    M1 --> M3 --> M4
    M2 --> M3
    M4 --> M5 & M6

    style Capabilities fill:#e8f5e9
```

### 4.4 底层存储层

底层存储层专注于三类对象的持久化落地，不包含任何业务逻辑：

| 对象类型 | 存储路径 | 存储内容 |
|---------|---------|---------|
| Blob | `.workspace/blob/` | 文件原始内容，以哈希值命名 |
| Tree | `.workspace/tree/` | 目录快照 JSON，以哈希值命名 |
| Commit | `.workspace/commit/` | 提交元数据 JSON，以哈希值命名 |

## 五、文件变更与版本联动

### 本章要点

| 阶段 | 说明 |
|------|------|
| 变更捕获 | 外部操作业务区文件 / toc.yml，内核实时感知 |
| 版本提交 | 扫描全空间 → 计算 Blob 哈希 → 生成 Tree 快照 → 生成 Commit |
| 版本对比 | 对比两个 Commit 关联的 Tree 差异 |
| 环境回滚 | 基于 Tree 快照还原全空间文件状态 |

### 5.1 变更捕获机制

外部通过 HTTP 接口操作业务区文件、修改 toc.yml 时，系统内核会**实时捕获**所有变更：

```mermaid
flowchart LR
    subgraph 外部操作["外部 HTTP 请求"]
        A1["创建文件"]
        A2["修改文件"]
        A3["删除文件"]
        A4["修改 toc.yml"]
    end

    subgraph 捕获["内核实时感知"]
        K["变更标记<br/>标记所有受影响的路径"]
    end

    A1 & A2 & A3 & A4 --> K

    style 外部操作 fill:#e1f5fe
    style 捕获 fill:#fff3e0
```

### 5.2 版本提交流程

当触发版本提交动作时，内核执行以下四步操作：

```mermaid
flowchart TB
    A["Step 1: 扫描全空间<br/>遍历所有业务区文件与 toc.yml"]

    B["Step 2: 计算 Blob 哈希<br/>对每个文件内容做 SHA256<br/>相同内容复用已有 Blob"]

    C["Step 3: 生成 Tree 快照<br/>记录全量路径 + 文件类型 + Blob 哈希<br/>形成当前时刻目录结构镜像"]

    D["Step 4: 生成 Commit<br/>关联当前 Tree + 父 Commit 哈希<br/>记录时间与说明<br/>追加到提交链"]

    A --> B --> C --> D

    style A fill:#e1f5fe
    style B fill:#e8f5e9
    style C fill:#fff3e0
    style D fill:#f3e0ff
```

### 5.3 版本对比与环境回滚

版本提交完成后，可基于提交链进行两类核心操作：

```mermaid
flowchart TB
    subgraph 对比["版本差异对比"]
        D1["选取两个 Commit"]
        D2["对比关联的 Tree"]
        D3["输出文件级差异<br/>新增 / 修改 / 删除"]
    end

    subgraph 回滚["环境回滚"]
        R1["选取目标 Commit"]
        R2["读取关联 Tree"]
        R3["还原全空间文件状态"]
    end

    D1 --> D2 --> D3
    R1 --> R2 --> R3

    style 对比 fill:#e1f5fe
    style 回滚 fill:#e8f5e9
```

## 六、对外接口设计

### 本章要点

| 能力场景 | 覆盖接口 | 安全机制 |
|---------|---------|---------|
| 空间初始化 | 创建工作空间、初始化目录结构 | 权限校验 |
| 文件操作 | 创建 / 读取 / 修改 / 删除文件 | 路径防穿透 |
| 目录操作 | 创建 / 遍历 / 删除目录 | 路径防穿透 |
| toc.yml 管理 | 读取 / 修改 / 校验 | 结构合法性校验 |
| 版本控制 | 提交 / 对比 / 回滚 | 完整性校验 |

### 6.1 五大核心场景

对外接口严格遵循 REST 规范，覆盖五大核心场景：

```mermaid
flowchart TB
    subgraph API["REST 接口 · 五大核心场景"]
        S1["空间初始化<br/>POST /workspace/init"]
        S2["文件操作<br/>CRUD /files/**"]
        S3["目录操作<br/>CRUD /dirs/**"]
        S4["toc.yml 管理<br/>GET/PUT /toc"]
        S5["版本控制<br/>POST /commit<br/>GET /diff<br/>POST /rollback"]
    end

    style API fill:#e1f5fe
```

### 6.2 安全校验机制

每个接口都做严格的路径校验，拦截跨目录穿透请求：

| 校验项 | 校验规则 | 拦截目标 |
|-------|---------|---------|
| 路径穿越 | 拒绝 `../` 等相对路径跳转 | 防止访问系统区外路径 |
| 系统区保护 | 拒绝所有 `.workspace` 路径访问 | 防止外部篡改版本数据 |
| 路径合法性 | 仅允许业务区合法路径格式 | 保障业务区隔离安全 |

请求响应格式统一，错误码遵循 HTTP 标准，对接逻辑简单、清晰、无歧义。

## 七、安全隔离体系

### 本章要点
