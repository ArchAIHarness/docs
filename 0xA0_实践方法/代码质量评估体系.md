# 代码质量评估体系

> **阅读对象**:架构师、技术负责人、Code Reviewer、质量平台建设者
> **前置阅读**:[团队协作开发指南](./团队协作开发指南.md) · [端到端研发交付 SOP](./端到端研发交付SOP.md)

一套**可量化、可对比、可治理**的代码质量评估方法论。不止于发现问题,更在于建立统一口径 —— 让团队对「什么算严重问题」有一致认知。

## 一、评估目标

建立统一的代码质量评估标准，确保团队对代码质量的判断口径一致，包含：

- **问题定级**：什么算 P0/P1/P2/P3，以及降级规则
- **评估维度**：评什么（代码结构、可靠性、资源管理等 10 个维度）及权重分配，融合阿里 P3C 规范
- **评估方法**：怎么审（grep patterns、检查清单、自动化工具）
- **报告规范**：怎么输出（模板、评分公式、汇总格式）
- **评估原则**：怎么判（证据优先、防御适度、避免误区）

目标：一次评估能产出可对比的历史报告，持续跟踪代码质量趋势。

## 二、问题定级标准

### 2.1 判定矩阵

| 级别     | 影响范围           | 利用条件          | 示例             |
| ------ | -------------- | ------------- | -------------- |
| **P0** | 编译失败/部署阻塞/运行崩溃 | -（内部问题）       | 编译报错、OOM、硬编码密码 |
| **P1** | 全局/核心功能不可用     | 无需条件，直接利用     | 登录返回500、数据泄露   |
| **P2** | 部分功能受损         | 需凭证/特定格式/一步操作 | 权限绕过、信息枚举      |
| **P3** | 潜在风险           | 需多步组合、特殊环境    | 日志噪音、代码冗余      |

### 2.2 P0 判定（立即阻断）

满足以下任一条件即为 P0，**立即阻断部署**：

| 维度 | 场景 | 判定条件 | 检测方式 |
|------|------|----------|----------|
| **编译/构建** | 语法错误 | Java 语法不合法，编译器报错 | `mvn compile` 失败 |
| **编译/构建** | 类型错误 | 泛型擦除、类型强转失败 | 编译报错 |
| **编译/构建** | 循环依赖 | A→B→A 的 Bean 循环 | 启动失败 |
| **编译/构建** | 构建失败 | Maven/Gradle 编译不通过 | `mvn package` 失败 |
| **启动** | Bean 注入失败 | @Autowired 找不到 Bean | 启动日志 |
| **启动** | 配置缺失 | application.yml 缺少必需配置 | 启动失败 |
| **运行** | **OOM** | 内存泄漏、大对象导致崩溃 | 实际运行/压测 |
| **运行** | **死锁** | synchronized 内等待对方释放锁 | 实际运行 |
| **运行** | **死循环** | while(true) 无出口、递归无终止 | 代码审查 |
| **运行** | 越界崩溃 | 数组/集合越界导致 JVM 崩溃 | 代码审查 |
| **代码** | 硬编码敏感信息 | 密码/密钥/Secret 在代码中明文 | grep pattern |
| **代码** | **分层违规** | Domain 层依赖 Infrastructure 层 | checkstyle/编译 |

> 🔴 **注意**：P0 是团队内部问题（红灯），不对外暴露，但必须立即修复才能继续开发/部署。

> **执行要点**：P0 问题由自动化工具（编译检查、循环依赖检测、分层约束）自动拦截，不需要人工评估。

### 2.3 P1 判定（全局/核心功能不可用）

满足以下任一条件即为 P1，**必须优先修复**：

| 维度 | 场景 | 判定条件 | 利用条件 | 检测方式 |
|------|------|----------|----------|----------|
| **可靠性** | 业务逻辑错误 | 核心业务流程实现与需求不符 | 直接触发 | 代码审查 |
| **可靠性** | 金额计算错误 | 浮点精度（double/float）、整数溢出 | 直接触发 | grep + 代码审查 |
| **可靠性** | 状态机缺陷 | 非法状态转换未拦截 | 直接触发 | 代码审查 |
| **可靠性** | **NPE 崩溃** | 空指针未捕获导致服务不可用 | 直接触发 | 实际运行 |
| **数据层质量** | **大表全扫** | >10 万行无分页无索引 | 直接触发 | 慢查询日志/explain |
| **数据层质量** | **N+1 查询** | 循环内查数据库且 >1000 条 | 列表操作触发 | 代码审查/日志 |
| **资源管理** | **OOM 风险** | 潜在内存泄漏（集合无限增长） | 长时间运行 | 压测/代码审查 |
| **健壮性** | 外部服务无兜底 | Feign/K8s Client 无 fallback 且超时未配 | 直接触发 | 代码审查 |
| **健壮性** | **并发缺陷** | 线程安全问题导致数据不一致 | 并发场景触发 | 代码审查 |
| **技术实现** | 算法逻辑错误 | 核心算法（排序/搜索）实现错误 | 直接触发 | 代码审查/测试 |
| **架构设计** | **长事务** | @Transactional 内调用外部服务 | 直接触发 | 代码审查 |

> 🟠 **注意**：P1 问题直接影响核心功能或生产稳定，**优先于功能开发修复**。

> **执行要点**：P1 问题需要人工评估，重点关注"利用条件"列，无需特殊条件即可触发的问题优先处理。

### 2.4 P2 判定（部分功能受损）

满足以下条件为 P2，**需在近期修复**：

| 维度 | 场景 | 判定条件 | 利用条件 | 检测方式 |
|------|------|----------|----------|----------|
| **可靠性** | 分支遗漏 | switch/if 未覆盖所有枚举值 | 枚举新增触发 | 代码审查 |
| **可靠性** | 边界条件缺失 | null、空字符串、超长输入未处理 | 特殊输入触发 | 代码审查 |
| **可靠性** | 泛型类型不安全 | ClassCastException 潜在风险 | 运行时触发 | 代码审查 |
| **可靠性** | 返回值错误 | null vs 空集合混淆 | 运行时触发 | 代码审查 |
| **数据层质量** | N+1 查询 | 循环内查数据库（数据量 <1000） | 列表操作触发 | 代码审查 |
| **数据层质量** | 大表无分页 | >1 万行无分页（量小/低频） | 分页查询触发 | 代码审查 |
| **数据层质量** | 缺少索引 | where 条件字段无索引（但无全扫） | 复杂查询触发 | explain 分析 |
| **健壮性** | **空 catch** | catch 块无日志无处理，异常被吞没 | 直接触发 | grep pattern |
| **健壮性** | 资源泄漏 | 流/连接/线程池未正确关闭 | 长时间运行 | 代码审查 |
| **健壮性** | 超时未配 | 外部调用无超时时间 | 网络异常触发 | 代码审查 |
| **健壮性** | 幂等性缺失 | 重复请求导致数据不一致 | 重试触发 | 代码审查 |
| **架构设计** | 分层违规 | Application 依赖 Infrastructure | 编译可检测 | checkstyle |
| **架构设计** | 跨层耦合 | Controller 直接操作 Repository | 编译可检测 | 代码审查 |
| **技术实现** | 过度设计 | 为用设计模式而用设计模式 | 维护时触发 | 代码审查 |
| **代码规范** | 命名不一致 | 命名不符合规范 | 编译可检测 | checkstyle |
| **代码结构** | 方法过长 | 60-80 行（未超 80 行） | 代码审查 | pmd |

> 🟡 **注意**：P2 问题影响局部功能，需要修复但可以规划到迭代中处理。

> **执行要点**：P2 问题可通过 grep patterns 和 checkstyle 自动化检测部分问题，需要人工确认修复优先级。

### 2.5 P3 判定（潜在风险）

满足以下条件为 P3，**规划改进**：

| 维度 | 场景 | 判定条件 | 检测方式 |
|------|------|----------|----------|
| **代码规范** | 重复代码 | 3 处以上相似逻辑（但简单） | pmd cpd |
| **代码规范** | 魔数未抽取 | 关键值未定义为常量 | checkstyle |
| **代码结构** | 方法偏长 | 40-60 行（未超 60 行阈值） | pmd |
| **代码结构** | 圈复杂度偏高 | 8-10（未超 10 阈值） | pmd |
| **代码结构** | 分支嵌套偏深 | 2-3 层嵌套（未超 3 层） | 代码审查 |
| **可靠性** | 防御性编程 | 当前未触发但未来可能（如除零） | 代码审查 |
| **资源管理** | 大对象分配 | 单次分配 >1MB 但非频繁 | 代码审查 |
| **健壮性** | 日志噪音 | 每请求 50+ 行 INFO 日志 | 日志分析 |
| **健壮性** | 缺少监控 | 关键业务无指标埋点 | 代码审查 |
| **健壮性** | 无 Trace | 无 MDC userId 透传 | 代码审查 |
| **数据层质量** | 缓存策略 | 热点数据未缓存但低频访问 | 代码审查 |
| **数据层质量** | 异步优化 | 可异步但同步执行（影响响应时间） | 代码审查 |
| **架构设计** | 可扩展性差 | 硬编码分支，策略模式可用但未用 | 代码审查 |
| **架构设计** | DDD 优化 | 聚合根粒度、领域事件设计可改进 | 代码审查 |
| **开发实践** | 测试覆盖不足 | 核心逻辑无测试覆盖 | 参考项 |

> 🟢 **注意**：P3 问题不影响当前功能，是潜在的改进点，可规划到技术优化迭代。

> **执行要点**：P3 问题可通过 pmd/checkstyle 自动化检测，建议定期清理。

### 2.6 升级/降级规则

#### 升级规则

| 原级别 | 目标级别 | 场景      | 触发条件                              |
| --- | ---- | ------- | --------------------------------- |
| P3  | P2   | 边界条件缺失  | null/空字符串/超长输入未处理，但不影响功能          |
| P3  | P2   | 代码冗余    | 重复代码 3+ 处，影响可读性                   |
| P3  | P2   | 方法过长    | 40-60 行，虽超但逻辑清晰                   |
| P2  | P1   | 边界条件缺失  | 参数可被恶意构造导致内存溢出或崩溃                 |
| P2  | P1   | 权限绕过    | 需改请求头但无需获取凭证                      |
| P2  | P1   | N+1 查询  | 数据量 >1000 且高频访问                   |
| P2  | P1   | 大表无分页   | 数据量增长预期快（>10 万/年）                 |
| P2  | P1   | 空 catch | catch 的是 RuntimeException，业务异常被吞没 |

#### 降级规则

| 原级别 | 目标级别 | 场景         | 降级原因           |
| --- | ---- | ---------- | -------------- |
| P1  | P2   | 需要数据库拖库    | 攻击成本极高，需先拖库    |
| P1  | P2   | 需要内网访问     | 需先渗透内网         |
| P2  | P3   | 需要有效 token | 攻击成本高，需先认证     |
| P2  | P3   | JPA 参数化查询  | SQL 由框架生成，自动安全 |
| P2  | P3   | 需 3+ 步组合   | 利用链过长          |
| P2  | P3   | 仅理论风险      | 数据模型无触发条件      |
| P2  | P3   | 重复代码简单     | 影响可读性但不影响功能    |
| P2  | P3   | 嵌套深但清晰     | 代码可读，嵌套必要      |
| P2  | P3   | 方法长但内聚     | 单一职责，无需拆分      |

## 三、评估维度

### 3.1 维度定义

评估维度分为三大类别，融合阿里 P3C 规范和 SonarQube 标准：

| 类别 | 维度 | 权重 | 核心评估点 | p3c规则映射 |
|------|------|------|-----------|-------------|
| **代码质量** | 代码结构 | 10% | 圈复杂度、嵌套深度、方法长度 | MethodTooLong |
| **代码质量** | 代码规范 | 5% | 命名、注释、格式化、魔数 | 命名规范、注释规范、常量规范 |
| **正确性** | 可靠性 | 20% | 逻辑错误、NPE、类型安全、精度 | 集合处理(BigDecimal/equals) |
| **运行时** | 资源管理 | 15% | OOM、内存泄漏、内存逃逸 | - |
| **运行时** | 数据层质量 | 15% | N+1、缺索引、无分页 | ORM规范 |
| **运行时** | 健壮性 | 10% | 异常处理、容错、幂等 | 异常处理、并发处理 |
| **设计** | 技术实现 | 10% | 设计模式、算法、并发安全 | OOP规范、并发规范、流程控制 |
| **设计** | 架构设计 | 5% | DDD分层、依赖方向、聚合根 | - |
| **工程** | 可观测性 | 5% | 日志、监控、Trace | - |
| **工程** | 开发实践 | 5% | TDD、测试覆盖率 | - |

> **参考标准**：
> - 阿里 P3C：49条规则（OOP 8条、集合 7条、并发 9条、异常 6条、流程控制 4条、命名 6条、常量 2条、ORM 1条、注释 6条、其他 7条）
> - SonarQube：可靠性(Security)、安全性(Maintainability)、可维护性(Bug)、性能(Performance)

### 3.2 评分标准（10分制）

```
9-10：优秀，接近生产就绪
7-8： 良好，有少量可优化点
5-6： 中等，存在明显问题但不影响核心功能
3-4： 较差，关键功能有缺陷
1-2： 很差，多处致命问题
```

### 3.3 维度评估细则

#### 3.3.1 代码结构（10%）

| 评估项 | 评估内容 | p3c映射 | 扣分标准 |
|--------|----------|---------|----------|
| 圈复杂度 | 方法分支数控制 | - | 复杂度 >10 -1，>15 直接 P1 |
| 嵌套深度 | if/for 嵌套层数 | - | >3层嵌套 -1，>5层 -2 |
| 方法长度 | 单方法代码行数 | MethodTooLong | 60-80行 -1，>80行 -2 |
| 分支数量 | switch/if 分支数 | - | >10分支建议重构 -1 |

**阈值参考（p3c）**：
- 方法长度：不超过 80 行
- 圈复杂度：不超过 10
- 嵌套深度：不超过 3 层

#### 3.3.2 代码规范（5%）

| 评估项 | 评估内容 | p3c映射 | 扣分标准 |
|--------|----------|---------|----------|
| 命名规范 | 类/方法/变量命名 | 命名规范(6条) | 不规范每处 -0.5 |
| 注释规范 | Javadoc、关键逻辑注释 | 注释规范(6条) | 关键逻辑无注释 -1 |
| 格式化 | 缩进、空格、换行 | - | 严重不统一 -1 |
| 魔数 | 硬编码数字/字符串 | 常量规范(2条) | 关键值未定义常量 -1 |

**p3c 命名规范要点**：
- 类名使用 UpperCamelCase
- 方法/变量使用 lowerCamelCase
- 常量使用 UPPER_SNAKE_CASE
- 集合类型后缀：List/Map/Set
- 布尔值前缀：is/has/can/should

#### 3.3.3 可靠性（20%）

| 评估项 | 评估内容 | p3c映射 | 扣分标准 |
|--------|----------|---------|----------|
| 业务逻辑 | 核心流程正确性 | - | 逻辑错误直接 P1 |
| NPE 防护 | 空指针未处理 | 集合处理(7条) | 潜在 NPE -1，崩溃 -P1 |
| 类型安全 | 泛型、强转安全 | - | ClassCastException -2 |
| 精度问题 | 浮点金额计算 | BigDecimal规范 | double/float金额计算 -2 |
| 分支覆盖 | switch/if 完整性 | - | 枚举值遗漏 -1 |
| 返回值 | 与接口契约一致 | - | null vs 空集合混淆 -1 |

**p3c 集合处理要点**：
- 禁止在 foreach 循环中 remove/add
- 使用集合工具类而非手动实现
- 集合判空使用 isEmpty()
- subList 不可直接修改

#### 3.3.4 资源管理（15%）

| 评估项 | 评估内容 | p3c映射 | 扣分标准 |
|--------|----------|---------|----------|
| 内存泄漏 | 对象未释放、集合无限增长 | - | 潜在泄漏 -2，OOM -P0 |
| 大对象 | 单次分配 >1MB 对象 | - | 频繁分配 -2 |
| 资源泄漏 | 流/连接/线程池未关闭 | - | 每处 -1 |
| 内存逃逸 | ThreadLocal 误用 | - | 异步后未清理 -2 |

**P0 判定**：内存泄漏导致 OOM 崩溃

#### 3.3.5 数据层质量（15%）

| 评估项 | 评估内容 | p3c映射 | 扣分标准 |
|--------|----------|---------|----------|
| N+1 查询 | 循环内查数据库 | - | 每处 -1，>1000条 -P1 |
| 缺索引 | where 字段无索引 | - | 慢查询 >1s -1 |
| 无分页 | 大表查询无分页 | ORM规范 | >1万行无分页 -1 |
| 全表扫描 | 无 WHERE 或索引失效 | - | >10万行全扫 -P1 |

**p3c ORM 规范要点**：
- 批量操作使用 batch insert/update
- 避免 N+1 查询，使用 JOIN 或批量查询
- 分页查询必须带 LIMIT

#### 3.3.6 健壮性（10%）

| 评估项 | 评估内容 | p3c映射 | 扣分标准 |
|--------|----------|---------|----------|
| 异常处理 | try-catch 覆盖合理 | 异常处理(6条) | 空 catch -1，业务异常被吞 -P2 |
| 容错机制 | Feign fallback | - | 无兜底且超时未配 -P1 |
| 幂等性 | 重复请求处理 | - | 不可重入导致数据不一致 -2 |
| 超时配置 | 外部调用超时 | - | 无超时配置 -1 |
| 并发安全 | 线程安全、资源竞争 | 并发处理(9条) | 并发缺陷 -2，死锁 -P0 |

**p3c 异常处理要点**：
- 禁止吞掉异常（至少记录日志）
- 禁止用异常做流程控制
- finally 块必须释放资源
- 自定义异常继承合理体系

#### 3.3.7 技术实现（10%）

| 评估项 | 评估内容 | p3c映射 | 扣分标准 |
|--------|----------|---------|----------|
| 设计模式 | 策略/工厂/模板方法 | OOP规范(8条) | 反模式 -1，过度设计 -1 |
| 算法正确 | 排序/搜索/计算逻辑 | - | 逻辑错误直接 P1 |
| 并发安全 | synchronized/volatile | 并发规范(9条) | 线程安全问题 -2 |

## 五、具体审查方法

### 5.1 快速发现问题的 grep patterns

> **执行要点**：grep patterns 用于快速发现潜在问题，发现后需人工确认是否真的是问题。

#### 5.1.1 P0 阻断检测（必须通过才能部署）

```bash
# 编译检查
mvn clean compile 2>&1 | grep -i "error\|failure"  # 编译失败 → P0

# 循环依赖检测
grep -rn "@Autowired\|@Inject" --include="*.java" | grep -E "import.*domain.*\.|import.*infrastructure.*\."  # 跨层依赖

# 硬编码敏感信息
grep -rn "password\s*=\s*[\"'][^\$]" --include="*.java" | grep -v "password.*\{|\.getenv\|System\.get"  # 密码硬编码 → P0
grep -rn "secret\s*=\s*[\"'][^\$]" --include="*.java" | grep -v "secret.*\{|\.getenv"
grep -rn "apiKey\s*=\s*[\"'][^\$]" --include="*.java"
```

#### 5.1.2 P1 全局问题检测

```bash
# 浮点金额计算（精度问题）→ P1
grep -rn "double\|float" --include="*.java" | grep -E "price|amount|money|fee|cost|金额|价格|费用" | grep -v "BigDecimal"

# N+1 查询检测 → P1（>1000条）/ P2（<1000条）
grep -rn "for.*{\|forEach" --include="*.java" | xargs grep -E "\.find|\.getId\(\)|\.getUserId\|repository\." | grep -v "cache\|map\|batch"

# 大表全表扫描 → P1
grep -rn "\.findAll\(\)" --include="*.java" | xargs grep -L "Page\|limit\|@Query.*LIMIT"  # 需人工确认数据量

# NPE 风险（Optional.orElse(null)）→ P1
grep -rn "\.orElse(null)" --include="*.java" | grep -v "Optional\<String\>"  # 需人工确认
```

#### 5.1.3 P2 部分问题检测

```bash
# 空 catch（异常被吞没）→ P2
grep -rn "catch.*Exception.*\}[\s]*$" --include="*.java" | grep -v "log\.\|throw\|throw new"

# 异常信息泄露 → P2
grep -rn "e\.getMessage\|e\.printStackTrace" --include="*.java" | grep -v "log\|throw\|new.*Exception"

# 资源泄漏（Stream/Connection 未关闭）→ P2
grep -rn "FileInputStream\|FileOutputStream\|Connection\|Statement" --include="*.java" | grep -v "try.*with|close\(\)" | head -20

# 无超时配置 → P2
grep -rn "@FeignClient" --include="*.java" | xargs grep -L "readTimeout\|connectTimeout"

# 跨层依赖 → P2
grep -rn "import.*infrastructure" --include="*.java" | grep -E "domain/|application/" | head -10
```

#### 5.1.4 P3 优化检测

```bash
# 重复代码检测
pmd cpd -d src/main/java -f text | grep -A2 "Found a duplicated code fragment"  # >3处重复 → P3

# 方法过长检测（40-60行）
grep -rn "public\|private\|protected" --include="*.java" | wc -l  # 需配合 pmd 检测

# 魔数检测
grep -rn "[0-9]\{4,\}" --include="*.java" | grep -v "^[0-9]\{4,6\}$" | grep -v "200\|404\|500" | grep -v "0\.\|1\.\|10\." | head -20

# 日志噪音检测
grep -rn "log\.info\|log\.debug" --include="*.java" | wc -l  # 需人工确认每请求行数

# ThreadLocal 未清理 → P3
grep -rn "ThreadLocal" --include="*.java" | grep -v "remove\(\)" | head -10
```

#### 5.1.5 p3c 规范快速检测

```bash
# PO002: 覆写方法必须加 @Override
grep -rn "public.*\(.*\).*\{$" --include="*.java" | xargs grep -L "@Override" | xargs grep -n "extends\|implements" | head -10

# PC001: forEach 中 remove/add
grep -rn "forEach.*->" --include="*.java" | xargs grep -n "remove\|add" | head -10

# PC002: 集合判空用 isEmpty()
grep -rn "==\s*null\|!=\s*null" --include="*.java" | grep -E "\.size\(\)|\.length" | head -10

# PT003: 线程池禁止用 Executors
grep -rn "Executors\." --include="*.java" | grep -v "Executors\.newSingleThread\|Executors\.newCachedThread"

# PE001: 禁止吞掉异常
grep -rn "catch.*\{[\s]*\}" --include="*.java" | grep -v "log\|throw\|throw new"

# PK001: 禁止魔法数字（需配合 checkstyle）
grep -rn "[=\(]\s*[0-9]\{3,\}\s*[;,\)]" --include="*.java" | grep -v "[0-9]\{4,6\}" | head -20
```

#### 5.1.6 一键快速扫描命令

```bash
# 快速扫描（5分钟内）：检测高优先级问题
#!/bin/bash

echo -e "\n=== N+1 查询检测 ==="

echo -e "\n=== 空 catch 检测 ==="
grep -rn "catch.*Exception.*\}[\s]*$" --include="*.java" | grep -v "log\|throw" | head -5 || echo "未发现"

| 模式                                             | 风险     | 例子                                 |

> **执行要点**：按顺序执行，每步完成后记录结果。

```

### 7.3 评分计算公式

```
维度得分 = 10 - Σ(各问题扣分)

最终得分 = Σ(各维度得分 × 权重)
```

**评分与P级的关系**：

| P级 | 说明 | 对维度得分的影响 |
|-----|------|------------------|
| **P0** | 立即阻断部署 | 该维度直接计 0 分 |
| **P1** | 必须优先修复 | 该维度直接计 ≤3 分 |
| **P2** | 近期修复 | 该维度每次 -1 分 |
| **P3** | 规划改进 | 该维度每次 -0.5 分 |

**执行要点**：
1. **发现 P0 问题** → 该维度直接归零 → 停止评估 → 必须修复后重新评估
2. **发现 P1 问题** → 该维度 ≤3 分 → 综合评分 ≤7 分 → 建议不合并代码
3. **发现 P2/P3 问题** → 按扣分表计算 → 综合评分作为技术债参考

**扣分速查表**：

| 维度 | P1 问题（严重） | P2 问题（一般） | P3 问题（轻微） |
|------|-----------------|-----------------|-----------------|
| 代码结构 | 圈复杂度 >15 -5 | 圈复杂度 >10 -1/处 | 圈复杂度 8-10 -0.5/处 |
| 代码规范 | - | 命名不规范 -1/处 | 魔数未抽取 -0.5/处 |
| 可靠性 | 逻辑错误 -5 | 边界遗漏 -1/处 | 防御性编程 -0.5 |
| 资源管理 | OOM风险 -5 | 资源泄漏 -1/处 | 大对象分配 -0.5 |
| 数据层质量 | 大表全扫 -5 | N+1 -1/处 | 缺索引 -0.5 |
| 健壮性 | 无fallback -5 | 空catch -1/处 | 无监控埋点 -0.5 |
| 技术实现 | 算法错误 -5 | 过度设计 -1/处 | API版本不兼容 -0.5 |
| 架构设计 | 长事务 -5 | 分层违规 -1/处 | DDD优化 -0.5 |
| 可观测性 | - | 日志噪音 -1 | 缺少指标 -0.5 |
| 开发实践 | - | - | 测试不足 -0.5（参考） |

**示例计算**：

```
假设评估发现以下问题：
- 代码结构：嵌套深度>5层（P2，-1）
- 可靠性：边界条件遗漏1处（P2，-1）
- 数据层质量：N+1查询2处（P2，-2）
- 健壮性：空catch 1处（P2，-1）
- 可观测性：日志噪音（P2，-1）

计算：
代码结构：10 - 1 = 9.0 × 10% = 0.9
代码规范：10 × 5% = 0.5
可靠性：10 - 1 = 9.0 × 20% = 1.8
资源管理：10 × 15% = 1.5
数据层质量：10 - 2 = 8.0 × 15% = 1.2
健壮性：10 - 1 = 9.0 × 10% = 0.9
技术实现：10 × 10% = 1.0
架构设计：10 × 5% = 0.5
可观测性：10 - 1 = 9.0 × 5% = 0.45
开发实践：参考项不计入

综合得分 = 0.9 + 0.5 + 1.8 + 1.5 + 1.2 + 0.9 + 1.0 + 0.5 + 0.45 = 8.75/10
```

**评分等级说明**：

| 分数 | 等级 | 说明 | 处理建议 |
|------|------|------|----------|
| 9-10 | 优秀 | 接近生产就绪 | 可直接发布 |
| 7-8 | 良好 | 有少量可优化点 | 可发布，建议下次迭代优化 |
| 5-6 | 中等 | 存在明显问题 | 建议修复 P2 后发布 |
| 3-4 | 较差 | 有关键缺陷 | 建议修复 P1 后发布 |
| 1-2 | 很差 | 多处致命问题 | 必须修复 P0/P1 后重新评估 |

> **p3c 扣分映射**：违反 p3c 规则的，每条规则 -0.5 分（可量化追踪）
> **执行要点**：扣分不是目的，目的是量化问题严重程度，指导修复优先级

### P1 — ContainerController 越权访问风险
> 🟠 **严重程度**：P1（橙灯）
> **利用难度**：直接利用
> **影响范围**：用户可删除非本人的容器

**位置**：`interfaces/.../ContainerController.java:89`

**问题描述**：
deleteContainer 方法直接使用前端传来的 containerId，未校验容器归属关系。

**代码片段**：
```java
@DeleteMapping("/{containerId}")
public R<Void> deleteContainer(@PathVariable String containerId) {
    containerService.delete(containerId);
    return R.ok();
}
```

**分析**：
攻击者只需替换 containerId 即可删除任意容器，无需任何凭证。利用难度低，影响范围广。

**修复建议**：
在 Service 层校验 containerId 归属：container.getUserId().equals(currentUserId)

## 九、评估原则

### 9.1 评估准则

1. **证据优先**：每个结论必须有代码证据
2. **逻辑优先于安全**：代码逻辑错误和性能问题优先于安全风险检测
3. **利用链分析**：不仅描述问题，还要分析实际利用难度
4. **防御适度**：不过度防御"理论风险"
5. **分清主次**：P1 问题必须直接影响核心功能
6. **性能敏感**：大表全扫、O(n²) 算法等直接影响生产稳定性，优先检测

### 9.2 常见误区

| 误区 | 正确做法 |
|------|----------|
| "理论上可能有 XSS" | 需要实际可触发才定 P2 |
| "数据库拖库后泄露" | 除非有漏洞，否则不作为 P1 |
| "需要特殊格式触发" | JPA 生成 SQL 通常安全 |
| "没有单元测试" | 不是扣分项 |
| "没有使用设计模式" | 避免过度设计，KISS 优先 |
| "业务代码缺少注释" | 注释不能替代好代码，代码自解释优先 |
| "状态机太复杂" | 业务需要则必须，复杂状态必须用状态机 |

### 9.3 与 AGENTS.md 的关系

评估标准与 AGENTS.md 规范：
- AGENTS.md：**开发规范**（必须遵守）
- 本评估体系：**评估标准**（衡量现状）

评估中发现违反 AGENTS.md 的问题，必须引用具体条款。

### A.1 OOP 规范（8条）

- PO007: 类非 static 成员变量与对象共生命周期

### A.2 集合规范（7条）
- PC001: foreach 循环中禁止 remove/add
- PC002: 集合判空使用 isEmpty()
- PC003: 禁止使用 Arrays.asList() 作为集合引用
- PC004: subList 不可直接修改
- PC005: 使用集合工具类而非手动实现
- PC006: 集合转数组使用 toArray(T[])
- PC007: 泛型通配符? extends T 用于只读

### A.3 并发规范（9条）
- PT001: 资源必须同步访问
- PT002: 优先使用不可变对象
- PT003: 线程池禁止用 Executors 创建
- PT004: 并发操作使用原子类
- PT005: TimeUnit 使用
- PT006: ThreadLocal 在使用后清理
- PT007: 避免死锁（统一锁获取顺序）
- PT008: volatile 保证可见性
- PT009: 避免在 synchronized 中调用外部方法
