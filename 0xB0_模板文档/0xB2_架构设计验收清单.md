# 架构设计验收清单

> **阅读对象**:架构师、技术负责人、设计评审参与者、AI Review Agent
> **前置阅读**:[架构设计 SOP](../0xA0_实践方法/0xA5_架构设计SOP.md) · [架构设计文档模板](../0xB0_模板文档/0xB1_架构设计文档模板.md) · [架构设计验收报告模板](../0xB0_模板文档/0xB3_架构设计验收报告模板.md)

这是一份架构设计的**验收元规则**:定义人 AI 协作边界、ADR 决策记录、设计流程、验收标准与常见问题定位。它回答的不是「如何写架构设计」,而是「如何判断一份架构设计是否合格」。

## 一、人 AI 协作边界

**核心原则：人把控方向和取舍，AI负责能力增强**

| 角色 | 责任              | 边界   |
| -- | --------------- | ---- |
| 人  | 方向把控、取舍决策、验收质量  | 不可替代 |
| AI | 学习检索、分析利弊、检查一致性 | 依赖约束 |

**为什么这样分工？**

| 角色 | 优势             | 劣势         |
| -- | -------------- | ---------- |
| 人  | 方向感、取舍能力、懂人性   | 知识面有限、经验有限 |
| AI | 知识广、分析强、24小时在线 | 没有方向、不会取舍  |

**架构设计的核心是方向和取舍，这必须由人做。AI负责弥补人的知识盲区。**

**边界约束**：

- 「必须由人决策的事项」中列出的决策项,必须由人做,AI 不能替代
- AI可以做检查、检索、分析，但不能做决策
- 人可以参考AI的分析，但最终决策必须由人做出

## 二、决策记录(ADR)

*每次关键决策必须记录，用于后续追溯和复盘*

| ID | 决策 | 日期 | 决策人 | 上下文 | 结论 |
| -- | -- | -- | --- | --- | --- |
| -  | -  | -  | -   | -   | -  |

**ADR模板**：

```
# ADR-XXX: 决策标题

## 日期
[YYYY-MM-DD]

## 上下文
描述做出此决策的情况和约束条件。

## 决策
描述选择的方案。

## 结论
描述由此产生的影响。
```

## 三、设计流程

| 阶段      | AI做什么      | 人做什么   |
| ------- | ---------- | ------ |
| 1.梳理业务  | 检索同类业务架构案例 | 确定业务目标 |
| 2.技术架构  | 分析技术选型利弊   | 选择架构模式 |
| 3.应用架构  | 检查服务划分一致性  | 决策服务边界 |
| 4.部署架构  | 检查部署可行性    | 确认部署方案 |
| 5.非功能设计 | 分析性能/安全风险  | 确定质量目标 |
| 6.风险应对  | 检查风险覆盖完整性  | 决策应对策略 |
| 7.演进规划  | 分析演进路径     | 确定演进时机 |

## 四、必须由人决策的事项

**以下决策必须由人做出，记录在ADR中**

| 决策项          | 为什么必须人做          |
| ------------ | ---------------- |
| 架构模式（单体/微服务） | 依赖团队能力、业务约束、人性偏好 |
| 服务边界         | 依赖业务语义理解、团队规模    |
| 技术选型         | 依赖团队现有能力、技术债评估   |
| 演进时机         | 依赖业务发展判断、团队成熟度   |

## 五、AI 辅助检查

**AI可以做的检查，用于辅助人判断。以下检查项具体可操作**

### 一、每章必检项（量化标准）

| 章节 | 必检项 | 通过标准 | 常见错误 |
|------|--------|---------|---------|
| 1.1~1.7 | 内容填充完整 | 每章至少一条具体内容 | 照抄模板原文或"待定" |
| 2.2 | 架构图与分层表一致 | 图中组件与表格一一对应 | 图有BFF表没有 |
| 2.5 | SLA数值可验证 | 有具体数字（99.9%而非"高可用"） | 只有定性描述 |
| 2.6 | ADR≥1条 | 架构模式决策已记录 | ADR为空 |
| 3.2 | 业务能力矩阵完整 | 有业务域、核心能力、能力说明 | 只有"XX"占位符 |
| 3.3 | 限界上下文边界清晰 | 每个上下文有职责+边界说明 | 上下文职责重叠 |
| 3.5 | 链路完整 | 起点→终点全链路闭环 | 有起点没终点 |
| 4.2 | 架构形态与团队匹配 | MVP≤1服务/成长期≤4服务 | 小团队直接微服务 |
| 5.4 | 租户隔离策略定义 | 逻辑隔离或物理隔离已选 | 隔离策略模糊 |
| 6.2 | 服务有接口定义 | 路径+方法+说明完整 | 只有服务名无接口 |
| 7.1 | 资源配置具体 | CPU/内存/副本数有数值 | "按需扩展"无具体值 |
| 8.1 | SLA指标完整 | SLA/RTO/RPO/MTTR都有 | 缺少RTO/RPO |
| 9.1 | 风险矩阵≥3条 | 识别主要风险 | 只有标题无内容 |
| 10.1 | 演进阶段定义 | MVP/成长期/成熟期都有 | 阶段缺失 |

### 二、一致性检查（跨章验证）

**规则：3.x的服务必须在5.x和6.x中有对应定义**

检查步骤：
1. 提取3.x中所有限界上下文/服务名
2. 验证5.x存储选型中有对应数据存储
3. 验证6.x服务设计中有对应服务
4. 验证7.x部署架构中有对应Pod/副本

**常见问题识别**：
| 问题 | 定级 | 说明 |
|------|------|------|
| 服务A在3.x定义了但6.x没有 | P1 | 服务定义缺失 |
| 服务B在6.x定义了但7.x没有部署 | P1 | 无法部署 |
| 数据表在5.x定义了但无服务使用 | P2 | 孤立数据 |
| 接口在6.x定义了但3.x没有对应服务 | P1 | 接口无归属 |

### 三、约束闭环检查

**规则：每章的约束必须能在后续章节落地**

| 约束来源 | 必须在...落地 |
|---------|--------------|
| 2.5 SLA 99.9% | 7.6 高可用设计（多AZ/故障自愈） |
| 5.4 租户物理隔离 | 7.x 部署架构（独立库独立Pod） |
| 4.4 服务单一职责 | 6.x 服务边界清晰 |
| 2.5 响应时间 P99<200ms | 8.4 性能设计 + 7.x 资源配置 |
| 8.2 安全性（JWT） | 7.5 服务治理（认证机制） |

### 四、快速问题识别

**这些模式直接报 P1**：
- 任何章节出现"待定"、"XX"、"TODO" → 未填充完整
- 2.6 ADR表格全为空 → 关键决策未记录
- 7.x 章节缺失资源配置 → 无法部署
- 6.x 接口契约只有服务名无路径 → 接口不完整

**这些模式报 P2**：
- 示例图表与正文描述不一致
- 数字前后矛盾（3.x说4个服务，6.x只写了2个）
- 约束只有定性描述无定量指标
- 7.2.2 命名空间与实际环境不匹配

### 五、案例推荐（AI可检索）

| 场景 | AI能做什么 |
|------|-----------|
| 业务架构 | 检索同类业务的领域模型 |
| 技术选型 | 检索相似场景的技术方案 |
| 服务划分 | 检索成功/失败的服务拆分案例 |
| 演进路径 | 检索类似规模的演进历程 |

## 六、设计质量评估

**评估维度：结构质量、内容质量、决策质量**

**强制要求**:AI 执行检查后,必须输出结构化验收报告

**AI 评估输出格式**:按「问题编号 / 严重等级 / 证据位置 / 修复建议 / 是否阻断」输出验收报告

**以下条件全部通过，设计才算完成**

| 检查项       | 标准             |
| --------- | -------------- |
| 十章完整      | 每章至少有一条非占位符内容  |
| 2.6 ADR记录 | 关键决策已记录，人已确认   |
| 逻辑自洽      | 章节间无明显矛盾       |
| 可衔接       | 6.x接口契约可映射到脚手架 |

**验收流程**:AI Review Agent 按 [架构设计验收报告模板](../0xB0_模板文档/0xB3_架构设计验收报告模板.md) 输出验收报告 → 人确认 → 通过/不通过

## 七、常见问题定位

*使用模板时遇到问题，先在这里定位，再去对应章节修复*

### 问题现象 → 可能原因 → 检查位置

| 问题现象 | 可能原因 | 检查位置 |
|---------|---------|---------|
| 章节间数据矛盾 | 服务数/接口数前后不一致 | 3.x ↔ 5.x ↔ 6.x 交叉核对 |
| 服务无法部署 | 部署架构未定义或资源规划缺失 | 7.1/7.2 资源配置 |
| 性能指标无法达成 | SLA分解不合理或未考虑瓶颈 | 2.5.1/8.4 性能设计 |
| 租户数据泄露风险 | 隔离策略未定义或缺失 | 5.4 多租户隔离 |
| 服务间调用混乱 | 服务边界不清晰或依赖关系缺失 | 6.2/6.3 服务边界与依赖 |
| 演进时机难判断 | 触发条件未量化 | 10.3 演进触发指标 |
| 风险应对缺失 | FMEA未覆盖关键组件 | 9.1/9.2 风险分析 |
| AI无法辅助检查 | 约束过于模糊无法判断 | 每章"约束"必须具体可验证 |

### 设计文档自查清单

**开始使用前**：

- [ ] 理解业务目标（1.2 背景说明）
- [ ] 确定架构模式（4.2 决策树选择）
- [ ] 明确服务边界（6.2 服务设计）

**填充内容时**：

- [ ] 每章至少一条具体内容（非"待定"）
- [ ] 章节间约束可追溯（2.x → 5.x → 6.x → 7.x）
- [ ] 接口契约完整（路径、方法、说明）

**提交前检查**：

- [ ] 2.6 ADR记录关键决策
- [ ] 无章节间明显矛盾
- [ ] 部署架构可支撑服务设计（7.x 能放下 6.x 的服务）

### 典型错误对照

| 错误类型 | 错误表现 | 正确做法 |
|---------|---------|---------|
| 因果颠倒 | 先定技术选型再套业务 | 业务目标 → 技术约束 |
| 约束空洞 | "高可用"、"可扩展"无具体指标 | SLA具体数值可验收 |
| 服务过细 | 3人团队8个服务 | MVP阶段≤4个服务 |
| 过度设计 | 单体阶段引入服务网格 | 按演进阶段引入能力 |
| 约束缺失 | 服务边界定义但无依赖关系 | 6.3 必须有依赖图 |

### 问题快速修复索引

| 问题 | 去哪里修复 |
|------|-----------|
| 不知道选什么架构模式 | 4.2 架构模式决策树 |
| 服务边界模糊 | 3.3 业务限界 |
| 接口契约不完整 | 6.2.4 接口契约设计 |
| 部署架构不合理 | 7.1 计算架构 + 7.2 容器编排 |
| 非功能指标缺失 | 2.5 架构约束 + 8.x 非功能性设计 |
| 不知道怎么演进 | 10.3 演进触发 + 10.4 扩展边界 |
