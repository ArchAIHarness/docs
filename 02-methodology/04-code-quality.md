# 代码质量评估体系

> 一套**可量化、可对比、可治理**的代码质量评估方法论。
>
> 不止于发现问题,更在于建立**统一口径** —— 让团队对「什么算严重问题」有一致认知。

---

## 评估目标

建立统一的代码质量评估标准,确保团队对代码质量的判断口径一致,涵盖:

| 维度 | 内容 |
| --- | --- |
| **问题定级** | P0/P1/P2/P3 判定标准,以及升降级规则 |
| **评估维度** | 10 个维度的权重分配,融合阿里 P3C 规范 |
| **评估方法** | grep patterns、检查清单、自动化工具 |
| **报告规范** | 模板、评分公式、汇总格式 |
| **评估原则** | 证据优先、防御适度、避免误区 |

> 🎯 **核心目标**:一次评估能产出**可对比的历史报告**,持续跟踪代码质量趋势。

---

## 问题定级标准

### 判定矩阵(总览)

| 级别 | 影响范围 | 利用条件 | 示例 |
| --- | --- | --- | --- |
| 🟣 **P0** | 编译失败 / 部署阻塞 / 运行崩溃 | —(内部问题) | 编译报错、OOM、硬编码密码 |
| 🔴 **P1** | 全局 / 核心功能不可用 | 无需条件,直接利用 | 登录返回 500、数据泄露 |
| 🟡 **P2** | 部分功能受损 | 需凭证 / 特定格式 / 一步操作 | 权限绕过、信息枚举 |
| 🟢 **P3** | 潜在风险 | 需多步组合 / 特殊环境 | 日志噪音、代码冗余 |

### P0 · 立即阻断部署

满足以下任一条件即为 P0:

| 维度 | 场景 | 检测方式 |
| --- | --- | --- |
| 编译/构建 | 语法错误、类型错误、循环依赖 | `mvn compile` 失败 |
| 启动 | Bean 注入失败、配置缺失 | 启动日志 |
| 运行 | OOM、死锁、死循环、越界崩溃 | 实际运行/压测 |
| 代码 | 硬编码敏感信息(密码/密钥) | grep 扫描 |
| 代码 | 分层违规(Domain 依赖 Infrastructure) | checkstyle |

> 🟣 **P0 由自动化工具自动拦截,不需要人工评估**。

### P1 · 必须优先修复

| 维度 | 典型场景 |
| --- | --- |
| 可靠性 | 业务逻辑错误、金额计算错误(`double`/`float`)、NPE 崩溃 |
| 数据层 | 大表全扫(>10 万行)、N+1 查询(>1000 条) |
| 资源 | 内存泄漏潜在风险(集合无限增长) |
| 健壮性 | 外部服务无 fallback、并发缺陷导致数据不一致 |
| 架构 | 长事务(@Transactional 内调用外部服务) |

### P2 · 近期修复

| 维度 | 典型场景 |
| --- | --- |
| 可靠性 | 分支遗漏、边界条件缺失 |
| 数据层 | N+1(<1000 条)、缺索引 |
| 健壮性 | 空 catch、资源泄漏、超时未配 |
| 架构 | 分层违规、跨层耦合 |
| 代码 | 方法过长(60-80 行)、过度设计 |

### P3 · 规划改进

| 维度 | 典型场景 |
| --- | --- |
| 规范 | 重复代码(>3 处)、魔数未抽取 |
| 结构 | 方法 40-60 行、圈复杂度 8-10 |
| 健壮性 | 日志噪音、缺少监控埋点 |
| 数据层 | 缓存可优化、可异步未异步 |

### 升降级规则(摘要)

```text
P3 → P2:  边界条件影响功能
P2 → P1:  数据量增长预期快、影响范围扩大
P1 → P2:  攻击成本极高(需先拖库/渗透内网)
P2 → P3:  仅理论风险、无触发条件
```

## 评估维度(十大维度)

| 类别 | 维度 | 权重 | 核心评估点 |
| --- | --- | --- | --- |
| **代码质量** | 代码结构 | 10% | 圈复杂度、嵌套深度、方法长度 |
| **代码质量** | 代码规范 | 5% | 命名、注释、格式化、魔数 |
| **正确性** | 可靠性 | 20% | 逻辑错误、NPE、类型安全、精度 |
| **运行时** | 资源管理 | 15% | OOM、内存泄漏、内存逃逸 |
| **运行时** | 数据层质量 | 15% | N+1、缺索引、无分页 |
| **运行时** | 健壮性 | 10% | 异常处理、容错、幂等 |
| **设计** | 技术实现 | 10% | 设计模式、算法、并发安全 |
| **设计** | 架构设计 | 5% | DDD 分层、依赖方向、聚合根 |
| **工程** | 可观测性 | 5% | 日志、监控、Trace |
| **工程** | 开发实践 | 5% | TDD、测试覆盖率(参考项) |

> **参考标准**:阿里 P3C 49 条规则 + SonarQube 标准

## 评分体系

### 10 分制

```text
9 - 10:  优秀,接近生产就绪
7 -  8:  良好,有少量可优化点
5 -  6:  中等,存在明显问题但不影响核心功能
3 -  4:  较差,关键功能有缺陷
1 -  2:  很差,多处致命问题
```

### 计算公式

```text
维度得分 = 10 - Σ(各问题扣分)
综合得分 = Σ(各维度得分 × 权重)
```

### 评分与 P 级的关系

| P 级 | 对维度得分的影响 | 处理建议 |
| --- | --- | --- |
| 🟣 P0 | 该维度直接计 0 分 | 停止评估,必须修复 |
| 🔴 P1 | 该维度 ≤ 3 分 | 综合评分 ≤ 7,建议不合并 |
| 🟡 P2 | 每次 -1 分 | 加入修复计划 |
| 🟢 P3 | 每次 -0.5 分 | 规划技术债清理 |

### 评分计算示例

```text
发现问题:
- 数据层 N+1 查询 2 处       (P2, -2)
- 健壮性 空 catch 1 处        (P2, -1)
- 可靠性 边界遗漏 1 处        (P2, -1)
- 代码结构 嵌套 >5 层         (P2, -1)
- 可观测性 日志噪音           (P2, -1)

加权计算:
代码结构  : (10-1) × 10% = 0.9
代码规范  : 10     × 5%  = 0.5
可靠性    : (10-1) × 20% = 1.8
资源管理  : 10     × 15% = 1.5
数据层    : (10-2) × 15% = 1.2
健壮性    : (10-1) × 10% = 0.9
技术实现  : 10     × 10% = 1.0
架构设计  : 10     × 5%  = 0.5
可观测性  : (10-1) × 5%  = 0.45
开发实践  : 参考项不计入

综合得分 = 8.75 / 10
```

## 评估流程

```text
第一步:编译检查(P0)              —— 10 分钟
        mvn clean compile + dependency:tree

第二步:分层约束检查                —— 5 分钟
        checkstyle import-control

第三步:自动化扫描                  —— 20 分钟
        PMD + SpotBugs + Checkstyle

第四步:快速 grep 扫描              —— 15 分钟
        敏感信息、浮点金额、N+1、空 catch

第五步:手动审查确认                —— 60-120 分钟
        按 10 个维度的清单逐项审查

第六步:计算评分                    —— 10 分钟
        按公式计算各维度 + 综合得分

第七步:撰写报告                    —— 30 分钟
        填写模板,按优先级排序
```

### 评估时间参考

| 评估范围 | 预计时间 |
| --- | --- |
| 单个 Controller(~200 行) | 30 分钟 |
| 单个 Service(~500 行) | 60 分钟 |
| 单个微服务(2000-5000 行) | 4-6 小时 |
| 多服务评估 | 8-16 小时(需分工) |

## 快速发现问题的 grep patterns

### P0 检测(必须通过)

```bash
# 硬编码密码 → P0
grep -rn "password\s*=\s*[\"'][^\$]" --include="*.java" \
    | grep -v "getenv\|System\.get"

# 跨层依赖 → P0
grep -rn "import.*infrastructure" --include="*.java" \
    | grep -E "domain/|application/"
```

### P1 检测(优先修复)

```bash
# 浮点金额计算 → P1
grep -rn "double\|float" --include="*.java" \
    | grep -E "price|amount|money|fee" \
    | grep -v "BigDecimal"

# N+1 查询 → P1
grep -rn "for.*{\|forEach" --include="*.java" \
    | xargs grep -E "\.find|repository\." \
    | grep -v "cache\|map\|batch"

# 大表全扫 → P1
grep -rn "\.findAll()" --include="*.java" \
    | xargs grep -L "Page\|limit"
```

### P2 检测(近期修复)

```bash
# 空 catch → P2
grep -rn "catch.*Exception.*}[\s]*$" --include="*.java" \
    | grep -v "log\.\|throw"

# 无超时配置 → P2
grep -rn "@FeignClient" --include="*.java" \
    | xargs grep -L "readTimeout\|connectTimeout"
```

## 手动审查检查清单(摘要)

完整清单按 10 个维度逐项展开,以下是核心要点:

### 代码结构

- [ ] 方法长度 ≤ 80 行?
- [ ] 圈复杂度 ≤ 10?
- [ ] 分支嵌套 ≤ 3 层?

### 可靠性

- [ ] 金额计算是否使用 `BigDecimal`?
- [ ] null 判空是否使用 `isEmpty()` 而非 `== null`?
- [ ] forEach 中是否未 `remove`/`add`?

### 健壮性

- [ ] catch 块是否至少记录日志?
- [ ] 外部服务是否有 fallback?
- [ ] 线程池是否用 `ThreadPoolExecutor` 而非 `Executors`?

### 架构设计

- [ ] Domain 层是否不依赖 Infrastructure / Spring?
- [ ] Repository 接口是否在 Domain 层?
- [ ] 聚合根是否正确标识?

## 常见反模式速查

| 反模式 | 风险 | 示例 |
| --- | --- | --- |
| `new File(userInput)` | 路径穿越 | `new File("/uploads/" + filename)` |
| `String.format("select * from %s", table)` | SQL 注入 | 动态表名列名 |
| `catch(Exception e){}` | 异常吞没 | 无日志、无处理 |
| `user.setId(param.getId())` | 越权修改 | 直接用前端 ID |
| `double price = 0.1 + 0.2` | 精度问题 | 金额计算 |
| `for(Item i : list) { repo.find(i.getId()); }` | N+1 | 循环内查库 |
| `@Transactional` + 外部调用 | 长事务 | Feign 调用在事务内 |
| `@Async` + 非线程安全对象 | 并发问题 | ThreadLocal 在异步方法 |
| `System.out.println(password)` | 敏感泄露 | 日志打印敏感数据 |

## 自动化工具栈

| 工具 | 定位 | 检测能力 |
| --- | --- | --- |
| **SpotBugs** | JVM 字节码静态分析 | 安全漏洞、空指针、资源泄漏 |
| **PMD** | 源码级别规则检查 | 圈复杂度、重复代码、坏味道 |
| **Checkstyle** | 代码风格规范 | 命名、格式、分层约束 |
| **SonarQube** | 综合质量平台 | Bug + 漏洞 + 异味 + 覆盖率 |

### Maven 一键执行

```bash
# 一键运行所有检查
mvn clean verify -Psecurity-check

# 单独运行
mvn spotbugs:check      # 安全检查
mvn pmd:check           # 代码检查
mvn checkstyle:check    # 格式检查
mvn test                # 单元测试

# Git pre-commit hook
mvn checkstyle:check -q && mvn spotbugs:check -q
```

## 评分等级说明

| 分数 | 等级 | 处理建议 |
| --- | --- | --- |
| 9-10 | 优秀 | 可直接发布 |
| 7-8 | 良好 | 可发布,建议下次迭代优化 |
| 5-6 | 中等 | 建议修复 P2 后发布 |
| 3-4 | 较差 | 建议修复 P1 后发布 |
| 1-2 | 很差 | 必须修复 P0/P1 后重新评估 |

## 评估的核心原则

1. **证据优先** —— 每个问题必须有文件路径、行号、代码片段
2. **防御适度** —— 不为了发现问题而发现问题,关注真实风险
3. **避免误区** —— 不要把代码风味当作 Bug,区分主观偏好与客观缺陷
4. **可对比** —— 评估结果必须可量化,便于追踪趋势
